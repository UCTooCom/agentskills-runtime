# 技能并行机制（concurrent_skills）设计复核与评审意见

> **评审对象**：`.codeartsdoer/specs/concurrent_skills/` 目录
>
> - `research.md`（研究报告，含附录 B 架构师观点原文）
> - `spec.md`（需求规格，含 5.6 节"技能内容自动渐进式加载"补充需求）
> - `design.md`（技术设计，含模块 H–L、阶段 9–16）
> - `tasks.md`（82 个任务的任务分解）  
>   **评审日期**：2026-10-12  
>   **评审依据**：已逐条核对 `research.md` 附录 B 原文，并对关键事实性论断做了源码核验（见 §6 核验记录）  
>   **评审结论**：架构师的**核心论断正确且有差异化价值**，但观点存在**过度外推**与**范畴错位**；四份文档整体结构扎实、复用策略得当，但在**内部一致性、personalization 建模、预算与常驻冲突、任务匹配算法、优先级/依赖排序**五处存在可修正的硬伤。建议在进入编码前按本文 §5 的 P0 项修正。

## 1. 架构师观点原文回顾（附录 B 核心）

> "agentskills 开放标准本质就是提示词的工程化方案……我们应该把这些设计哲学更广泛的应用……研究一下我们是不是可以将类似的个性化机制做成 skills，比如叫 personalization 技能插件……然后研究一下 agentskills-runtime 当前是不是只支持技能的串行使用？因为我们要支持将一切都做成技能，肯定需要技能的并行使用机制……personalization 技能插件这样的技能可以是一直都加载有效使用的，并行还可以使用其他的技能，比如 sdd 技能和 cangjie-coder 等开发技能……这个机制也很符合现实世界的运行机制，人类就可以边说话边看东西边听。"

> "这里所说的技能并行机制，并不是指程序并发的意思……技能的并行，其实就是将多个技能可以同时添加到上下文中，使得多个技能同时对于大模型的输入都是有效的。这样大模型就可以表现出同时使用了多个技能的输出行为。而技能之间也就存在了依赖或者互斥的关系，依赖的技能应该同时加载，而互斥的技能就应避免同时加载。"

观点可拆为四条主张：

1. **技能并行 = 上下文级并行**（多技能 prompt 片段同时驻留上下文），而非程序并发。
2. **"一切皆技能"需要并行机制兜底**，否则"只支持串行"会让该哲学不完整。
3. **个性化应抽象为技能插件**（`personalization`），且 `always_on` 常驻，与 sdd / cangjie-coder 等并行生效。
4. **技能间存在依赖/互斥关系**，依赖同载、互斥避载。
5. （隐含）**人类多模态并发**是类比依据。

## 2. 架构师为什么会提出此观点（动因分析）

动因不在"缺一个并发特性"，而在于**哲学承诺与工程现实之间的裂缝**：

- **哲学完整性压力**："一切皆技能 / 技能优先"是一个强主张。但当技能只能靠 `tool calling` 按需触发时，模型的"工作上下文"里平时没有任何技能指令——技能是"被叫出来才存在"的。这等于把"技能优先"降级成了"技能可选"。架构师敏锐地感到：若技能不能**持续、并行地**作用于模型输入，"一切皆技能"就只是注册表层面的口号。
- **个性化能力的归口焦虑**：`AgentWorkspace` 已有 SOUL/IDENTITY/USER/MEMORY 八类文件，但它是**文件级配置**，游离于技能生命周期之外（无依赖/互斥/版本/启用态）。架构师想把"个性化"也纳入统一的技能抽象，避免两套机制并存。
- **能力天花板被发现**：工具级并行（一轮内调多个工具）虽存在，但每个技能的**完整指令体**只有在被显式调用 `get_skill_content` 后才进入上下文（`research.md` 3.2、spec 5.6 漂移分析已确认）。即"模型知道有技能，但看不到技能怎么用"。架构师要的是"技能指令常驻可见、可综合"。
- **差异化叙事需要**：GOAI 大赛、论文对标 deepseek-harness 的叙事下，上下文级技能并发是一个**可宣称"超越业界最佳实践"**&#x7684;切入点（`research.md` 5.3 结论：无产品同时具备"上下文并行 + 依赖/互斥 + 常驻"三要素）。

> 结论：动因是真实且合理的——它由"哲学 → 现实裂缝"驱动，而非拍脑袋。但下文指出，裂缝的**正确填法**与架构师给出的**具体填法**并不完全一致。

## 3. 架构师观点正确性评判

总体：**核心主张（1、4）正确且重要；主张（2）表述不精确；主张（3、5）存在范畴错位与过度外推。**

### 3.1 正确的部分（应予坚持）

| 主张          | 评价                | 理由                                                                      |
| ----------- | ----------------- | ----------------------------------------------------------------------- |
| 技能并行 ≠ 程序并发 | ✅ 完全正确，且是全文最关键的洞察 | 把问题从"系统并发"重定位到"prompt 上下文组合"，这是 LLM Agent 领域少有人讲清的正确心智模型。               |
| 上下文级多技能同时生效 | ✅ 正确              | 多技能指令体同时占上下文窗口、模型综合生成，是可行且被低估的能力。deepseek-harness 的 `pre-step` 注入已是其雏形。 |
| 依赖/互斥关系建模   | ✅ 方向正确            | 技能间确有隐式关系，显式化 `depends_on` / `conflicts_with` 是合理抽象。                    |
| 差异化定位       | ✅ 成立              | 经核验，业界产品确实没有把三者完整工程化（见 §6）。                                             |

### 3.2 不精确 / 需修正的部分

- **"当前只支持串行"是误导表述**：`SkillAwareAgent._registerSkillsAsTools()` 已把所有技能注册为工具，模型一轮内可调用多个工具（工具级并行已存在）。真正缺失的是**上下文级指令驻留**，不是"并行执行"。`research.md` 自身 §3.2 承认了工具级并行，但 §2.1 与摘要仍写"仅串行"——**叙事自相矛盾**（见 §4.1）。正确表述应为："技能指令平时不在上下文，模型需显式调用才能获取完整内容；缺乏上下文级的、可并行的指令驻留。"
- **"人类边说边看边听"是范畴错误（若用于设计论证）**：人类感官是部分并行 + 缓冲的，且**不稀缺**；LLM 上下文窗口是**稀缺、互斥、竞争注意力**的资源。把多技能注入类比成"多感官同时输入"，会掩盖一个核心张力——**注入越多，单技能注意力越稀释、越易指令冲突、越易上下文爆炸**。类比适合做直觉引子，**不适合作为"应多注入"的设计依据**。架构师若在设计中沿用该类比，会为"常驻多技能"提供错误正当性。
- **personalization 作为"技能"是范畴错位**：SOUL/IDENTITY/USER/MEMORY 是**状态/配置**，不是**过程性指令**。`Skill` 的 `instructions` 字段语义是"动作指引"，把人格/用户画像塞进 `instructions` 是语义滥用，会混淆工具链（检索、渲染、去重都按"可执行技能"处理）。更糟的是：`getCombinedMemory()` 已在注入这些文件（`research.md` 3.6），再套一层 `personalization` 技能存在**双重注入**风险（`design.md` 2.1.3 同时列了 `PersonalizationSkillPlugin → WS` 与既有 `getCombinedMemory` 路径，未声明互斥）。

### 3.3 过度外推 / 应降级的部分

- **`always_on` 常驻被严重低估风险**：架构师强调 personalization "一直加载"，并举例"并行还能用 sdd / cangjie-coder"。但 sdd、cangjie-coder 是**任务型**技能，不应常驻。若把能力型技能也常驻，会与上下文预算直接碰撞（`design.md` 默认 `total_budget_tokens=8192`，`reserved_for_always_on=0.3` ≈ 2457 token，几个常驻技能即占满）。"人类多感官"类比恰恰掩盖了这个张力。
- **P3"超越业界"头脑风暴多属推测/不可行**（`research.md` 8.4）：语义向量检测指令冲突（只测文本相似度，测不出"矛盾输出格式"）、CSP/SAT 求解（约束系统极小，贪心优先级即可，上 SAT 是过度工程）、溯源标记（依赖模型自报受哪个技能影响，不可靠）、权重衰减（"10 轮未触发"阈值任意）。这些是**未来研究**，不应与可交付物混排。
- **5.6 补充需求是范围蔓延且与预算论题自相矛盾**："框架自动注入完整 instructions"与"上下文预算管理"在同一设计里并存——自动全量注入恰恰最容易冲破预算。`design.md` 用 `BudgetManager.allocateWithDegrade`（降级为 frontmatter）缓解，但默认行为（自动全量注入）对上下文是危险的，应默认更保守。

## 4. 设计文档合理性复核

### 4.1 内部一致性问题（必须修）

1. **"只串行"自相矛盾**：`research.md` §2.1/摘要称"仅串行"，§3.2 又称"工具级并行已存在"。需统一为"缺上下文级并行"。
2. **优先级/依赖排序矛盾（硬伤）**：`design.md` §2.4.2 的**漂移修复最小路径**为 `阶段1→2→3→9→12→13→14`（标 P0），但 `阶段12(SkillAutoInjector)` 依赖 `阶段11(BudgetManager)`，而 `阶段11` 被标 **P2**。即 **P2 模块落在 P0 关键路径上**，优先级标注自相矛盾。要么把 `BudgetManager` 提为 P0，要么让 `SkillAutoInjector` 的漂移路径在缺 `BudgetManager` 时退化为"仅按优先级淘汰、不做降级"（推荐后者，降级本就是增强）。
3. **`conflicts_with` 非对称处理弱**：`design.md` 2.2.2.3 对"单向声明"仅告警并按声明方处理。冲突在语义上是对称的，应在解析期**自动对称化**，消除告警分支。
4. **`compatible_with` 已定义但无消费者**：`research`/`spec`/`design` 均定义 `compatible_with`，但无任何消费逻辑。属死配置——要么落地（如作为预算优先级弱信号），要么删除。

### 4.2 建模问题

1. **personalization 双重注入风险**：未明确"启用插件时关闭 `getCombinedMemory()` 旧路径"。若不关闭，个性化内容会被注入两次（且格式不同），浪费上下文并可能造成指令重复。
2. **`metadata: HashMap<String,String>` 承载列表字段脆弱**：`depends_on` 以逗号分隔存字符串，技能名含逗号即解析错误。建议用 frontmatter 原生列表字段承载，而非塞进 `metadata`。
3. **注入所有权不清**：`WebMCPProtocol`（系统提示，构建一次）与 `WsChatController`（每轮消息）都接入 `SkillAutoInjector`。需明确：**系统提示只放 `always_on`（常驻层），每轮只放任务匹配层**，且每轮不得重复注入常驻层；否则要么常驻层每轮重注入浪费，要么任务层误入系统提示。设计靠"幂等+去重"兜底，但所有权边界应显式声明。

### 4.3 算法问题（有实证反例）

1. **`TaskMatcher` 默认 `keyword`+Jaccard 在其自带示例中即失败**：`design.md` §2.2.2.11 示例"编写仓颉代码实现用户登录" vs cangjie-coder 描述，Jaccard=0.3 < 阈值 0.6 → **不注入**，但明显应注入。说明默认策略+阈值**系统性欠注入**。`task_match_strategy` 默认应改为 `semantic`/`hybrid`（embedding），或对 `keyword` 采用 BM25/TF-IDF + 中文分词并重新标定阈值；并附一小份标注评测集校准。

### 4.4 预算与成本问题

1. **`total_budget_tokens=8192` 是魔法数**：相对 32k–200k 的模型窗口过小且固定。应**由模型上下文窗口派生**（如窗口的 15–20%），否则在大模型上预算形同虚设、在小模型上又可能溢出。
2. **"并行有效性"无验收标准**：上下文并行**使能**多技能综合，但**不保证**模型真能综合（推理级并行是涌现的）。`spec.md`/`design.md` 缺"技能组合效果评测"（如组合指令遵循率基准），导致"并行"是否真有用无法验证。

### 4.5 值得肯定的部分

- 三层并行模型（上下文/编排/推理）分层清晰，且与程序并发做了明确切割。
- 复用策略克制：`metadata` 扩展、复用 `SkillDependencyResolver`、保留 `get_skill_content` 作后备、字段可选+默认值保证 49 个存量技能向后兼容——这些都降低了风险。
- 测试矩阵（单元/集成/性能/回归）覆盖度高；回滚方案（功能开关、`Option` 包裹、`.env` 降级）完备。
- 对 `buildAgentFromDefinition` 空技能管理器缺陷的捕获是真实且高价值的（虽属独立 bug，顺带修正确实该做）。

## 5. 改进建议与补充（按优先级）

### P0（进入编码前必须修正）

- **A1 统一叙事**：全文将"只支持串行"改为"缺上下文级指令驻留/并行"，与 §3.2 的工具级并行表述对齐；明确"并行 = 上下文多技能同时有效，非程序并发"。
- **A2 修正优先级矛盾**：将 `BudgetManager` 提为 P0，或让 `SkillAutoInjector` 漂移路径在无 `BudgetManager` 时退化为"按优先级淘汰、不做降级"（推荐）。同步修正 `tasks.md` 关键路径（TG01→02→03→13→15→18 不应隐含依赖 TG17）。
- **A3 修复 TaskMatcher 默认策略**：默认改 `semantic`/`hybrid`；若保留 `keyword`，改用 BM25/TF-IDF + 中文分词并重新标定阈值（使其自带示例能通过），附标注评测集。
- **A4 明确注入所有权**：系统提示 = 常驻层（`always_on`）仅构建一次；每轮 WS 消息 = 任务层（任务匹配）且对常驻层去重、不重注入。

### P1（建模纠偏，强烈建议）

- **A5 personalization 改建模为"上下文层/ContextProvider"而非 `Skill`**：引入极简 `ContextProvider` 抽象（既可由个性化文件实现，也可由常驻技能实现），`personalization` 作为 profile 层接入；**启用插件时关闭 `getCombinedMemory()` 旧注入路径**，杜绝双重注入。若坚持"技能"术语，至少在 design 中显式声明二选一、不可并存。
- **A6 `conflicts_with` 解析期对称化**；**删除未消费的 `compatible_with`**。
- **A7 列表字段迁到 frontmatter 原生列表**（不塞 `metadata` 逗号串）。
- **A8 `total_budget_tokens` 由模型窗口派生**，并区分"常驻保留预算"与"任务层预算"。

### P2（增强，锦上添花）

- **A9 采用分层上下文模型替代扁平优先级队列**：
  - Layer 0 身份层（`always_on`，不可淘汰：SOUL/IDENTITY 级不变量）
  - Layer 1 能力层（按需、预算受控）
  - Layer 2 任务层（每轮、预算受控）  
    比纯 `priority`+`budget` 更清晰，天然化解"常驻 vs 预算"冲突，也更符合"personalization 常驻、sdd 按需"的直觉。
- **A10 常驻技能最小化**：仅身份/人格级不变量常驻；sdd、cangjie-coder 等能力/任务技能**不**设 `always_on`（与架构师举例相反，但符合预算现实）。
- **A11 动态优先级**：`priority` 作基础值，叠加任务相关度（TaskMatcher 的 `matchScore`）得到"有效优先级"，避免静态优先级在跨任务场景下失灵。

### P3（移到"未来研究"，不与交付物混排）

- **A12 将 CSP/SAT、语义向量冲突检测、溯源标记、权重衰减**从 design 主文档挪至独立的"Future Research"章节，标注为非阻塞、待验证，避免范围蔓延与过度工程预期。

### 补充：验收与评测（被遗漏的关键一环）

- **A13 增列"上下文并行有效性"验收基准**：给定"同时需要 sdd + cangjie-coder 指令"的任务，验证模型输出是否**同时遵循**两套指令（而非只遵循其一或互相矛盾）。无此基准，"并行"只是"注入了"，不等于"生效了"。

## 7. 总体结论

架构师提出"技能并行"的**动机正当、核心论断（上下文级并行 ≠ 程序并发；依赖/互斥建模）正确且有真实差异化价值**——这是本 spec 最值得保留的洞见，也是相对 deepseek-harness / OpenClaw / Hermes 的潜在超越点。

但设计在落地时出现了三类偏移：

1. **表述与事实错位**（"只串行"、"人类多感官"类比）掩盖了"上下文稀缺性"这一真正约束；
2. **personalization 被错误地建模为 `Skill`**，且未解决与既有 `getCombinedMemory` 的双重注入；
3. **常驻多技能与上下文预算的根本张力被低估**，而 `TaskMatcher` 默认算法在其自带示例中即失败、`BudgetManager` 被错标 P2 却卡在 P0 关键路径。

文档的复用策略、测试矩阵、回滚方案均属上乘，**修正 §5 的 P0/P1 项后即可进入编码**；P2 的分层上下文模型建议本轮就采纳（它一劳永逸地化解常驻/预算冲突），P3 的"未来研究"应与交付物解耦。

一句话：**方向对、野心大、细节有坑；修掉四处硬伤，这是一个能成立的、有差异化的好设计。**

# 附录 A：第二轮回应（针对架构师 2026-10-13 反馈）

> 背景：架构师就本报告 §3.2/§5-A5（"personalization 作为 Skill 是范畴错位，应改建模为 ContextProvider"）提出反驳，澄清了"为什么必须是 skill"的根因。本附录记录**核验依据、我的立场修正、以及改进后的方案**。

## A.1 我上一轮的偏差：撤回"应改为非 Skill 载体"的建议

我上一轮把问题框定为"**单节点上下文注入的语义纯度**"，据此建议 personalization 不要做成 Skill。这个建议**漏掉了跨节点分发这个一阶诉求**，因此是片面的，予以撤回。

架构师澄清后的真实根因是：**为了让一个智能体在网络的不同节点上表现一致，决定其行为的全部提示词（含 SOUL/IDENTITY/USER）必须随智能体一起在网络间传输；而只有"技能"这条通道已经具备了成熟的传输与持久化基础设施。**

这不是"把配置硬塞进技能"，而是**选择已有的、可工程化管理的分发单元来承载散落的提示词**。这个判断成立。

## A.2 经核验的事实依据（支撑架构师立场）

| 核验项                      | 结果 | 依据                                                                                                                                                                                                                                              |
| ------------------------ | -- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent_skills` 表存在且元数据完备 | ✅  | `sql/uctooDB.sql:512+`（`source`/`source_url`/`branch`/`tag`/`commit`/`version`/`author`/`license`/`keywords`/`status`/`runtime_status`…）—— 这正是"工程化管理"所指，且观点原文第一句"本质是提示词工程化方案"落到了实处                                                              |
| 文件系统 ↔ 数据库**双向同步**已具备    | ✅  | `.codeartsdoer/specs/skill-sync-system/spec.md` §1.1 双存储机制；§1.2 范围含"文件系统变更监听与数据库更新 / 数据库变更监听与文件系统更新 / **冲突检测与解决策略**"                                                                                                                            |
| 标准原文支持"用户上下文入技能"         | ✅  | `apps/agentskills/README.md`："packaging procedural knowledge and **company-, team-, and user-specific context** into **portable, version-controlled folders**"；"**Cross-product reuse**" —— 把 user-specific context 打包为可移植技能，是标准**已声明的意图**，不是误用 |
| 尚无既有的 profile 建模与之冲突     | ✅  | `.codeartsdoer/specs/profile/` 为**空目录**（占位），本方案无 incumbency 冲突，可安全落地                                                                                                                                                                            |

**结论**：我的"范畴错位"批评**言之过重**——标准是明文鼓励把 user-specific context 装进便携、版本化的技能目录的。架构师承认的"错位"，更准确的表述是"**语义判别不足**"（见 A.3/A.4.1），而非"放错了容器"。


## A.3 修订后的立场

**认可**：把散落的提示词（SOUL/IDENTITY/USER/MEMORY）归集为 skills、复用既有 skills 机制做工程化管理、并借 `agent_skills` 表 + 双向同步 + 开放 API 实现跨节点分发——**这条路线正确，我支持**。它同时兑现了：补 frontmatter、纳版本与依赖/互斥、可审计、可传输、可复用于异构智能体网络。

**但保留的下位担忧**（需靠精化解决，不能靠"错就错了"解决）：双重注入、常驻预算、以及**本轮新暴露的最大缺口——跨节点多写者的变更性与冲突语义**（A.4.2）。

## A.4 更好的方案：Profile-as-Skill（五项精化）

### A4.1 加类型判别式 `skill_type`（关键）

不要让它"伪装成可执行能力技能"。在 frontmatter 里显式声明：

```yaml
skill_type: profile      # profile | capability(默认)
load_policy: always_on
sync_scope: agent_owned  # A4.2
```

运行时据此**差异化绑定**：profile 类技能注入到**预留的 profile 上下文层**、不注册为工具、不被预算淘汰（但受层内上限约束）；capability 类走常规路径。这样既拿到了"技能作为分发单元"的全部好处，又诚实声明了"这是被承载的提示词，不是可执行能力"——正好消解架构师自己承认的那点错位。

### A4.2 补分发语义：变更性与归属（本轮最大增量，原设计完全缺失）

这是我认为**当前设计最需要做补充**的一点。四类文件的变更特征完全不同：

| 文件                        | 变更性             | 归属         | 建议复制策略                        |
| ------------------------- | --------------- | ---------- | ----------------------------- |
| `SOUL.md` / `IDENTITY.md` | 稳定、低频           | 智能体固有      | **可自由复制**（主节点权威，多节点只读）        |
| `USER.md`                 | 中频              | 用户级、跨智能体共享 | 复制，**以用户为权威**                 |
| `MEMORY.md` / 日常记忆        | **每会话、每节点持续写入** | 节点局部       | **不要盲目复制** —— 多节点并发写必然冲突/回写抖动 |

已有的 `skill-sync-system` 解决的是**单节点内 fs↔db 双向冲突**；而架构师设想的是**跨节点 ring/distributed 的多写者复制**，二者量级不同，**不能简单复用**。建议在 frontmatter 增加分发元数据并由演示层的同步逻辑消费：

```yaml
sync_scope: agent_owned | user_owned | node_local
authoritative: <node/agent/user id>
conflict_policy: last_write_wins | merge | manual
version: 1.2.0
etag / checksum: <hash>     # 用于判定脏否、避免无谓传输
```

> 若 MEMORY 也要求跨端漫游，这是个**真研究问题**（类 CRDT / 事件溯源合并），建议明确列为独立子课题，不要塞进 P0 主链路。

### A4.3 身份锚定：`agents` 表存**引用**而非正文

架构师担心"归集进 agents 数据错位更严重"——这个担心**正确**，但解法不是二选一。**不要让 `agents` 表承载提示词正文**，而是让 agent 记录持有**指向其 profile 技能的引用**（如 `profile_skill_ref` / 关联表）。这样：

- 同一性锚点仍是 `agents` 行（便于整体打包"这个智能体"并网络传输）
- 提示词正文仍是 skill（复用传输、版本、同步、失效通知）
- 不存在"把 prompt 硬塞进 agents 表"的错位

空的 `.codeartsdoer/specs/profile/` 目录可作为该关联模型的自然落点。

### A4.4 聚合注入，而非碎片常驻（回应预算担忧）

若 SOUL/IDENTITY/USER/MEMORY 各自成为一个 `always_on` 技能 → 4+ 常驻技能直接冲击预算（呼应原报告 A-points）。建议：**同步粒度保持分条**（便于独立生命周期与按需过期校验），但**注入时由组装器合成一个连贯的 `<profile_context>` 块**，占用 profile 层专属预算。既保留 granularity，又不炸上下文。

### A4.5 单一真源与迁移（消除双重注入）

一旦 profile skill 存在，它**就是唯一真源**；`AgentWorkspace.getCombinedMemory()` 须改为**从 profile skill 读取**或在启用时关闭，杜绝"（文件 + 技能）双份注入"。配套提供一次性迁移：为存量 SOUL/IDENTITY/USER/MEMORY **自动生成带 frontmatter 的 SKILL.md**（这恰好直接兑现架构师指出的"它们缺少 frontmatter、未被工程化管理"的痛点）；无 profile skill 时回退旧文件读取，保证向后兼容。

## A.5 一个叙事/合规风险提醒（重要）

标准原文说技能是 **"agents load on demand"**（按需加载）。因此 `load_policy: always_on` 的常驻加载**是本运行时的扩展，而非 agentskills 标准的要求**。

建议：在论文/大赛/标准对照材料里**明确标注这是扩展**（并可包装为对标准的建设性补充提案），不要写成"agentskills 标准支持常驻技能"。否则在 deepseek-harness 对照、标准符合性论述中会成为可被质疑的硬伤。

## A.6 仍然有效的原有结论（不因本轮撤回而失效）

- **P0 硬伤四条**：TaskMatcher 默认 keyword+Jaccard 在其自带示例即失败（应改 semantic/hybrid + 重标定阈值）；`BudgetManager` 标 P2 却卡在 P0 关键路径；`WebMCPProtocol` 与 `WsChatController` 注入所有权不清；"只支持串行"表述需统一为"缺上下文级驻留"。
- **不要因传输诉求而放大常驻范围**：sdd、cangjie-coder 是任务型技能，不应 `always_on`；只有 profile 层（A4.1）该常驻。
- **无验收基准则不算生效**：仍需"多技能组合遵循率"基准（A13）。
