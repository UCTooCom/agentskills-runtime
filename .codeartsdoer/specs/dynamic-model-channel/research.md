> 配套：`problem-analysis.md`（现状证据）、`spec.md`（需求）、`design.md`（架构）
> 日期：2026-10-02

## 1. 业界同类方案速览

| 方案 | 形态 | 通道如何定义 | 切换是否重启 | 协议扩展方式 | 对我们的可借鉴度 |
|---|---|---|---|---|---|
| **LiteLLM** | Python 网关（Proxy + SDK） | `config.yaml` 声明 `model_list`（`model_name` → `litellm_params`） | 支持**热重载** config（改 YAML 不重启 proxy） | Python 代码里加 `CustomLLM` 类 / 回调 | ⭐⭐⭐⭐ 配置驱动 + 别名映射 + 热重载 = 我们的主要参照 |
| **OpenRouter** | 托管聚合网关 | 平台侧维护模型清单，用户只带一个 key | 无需重启（远端数据） | 平台闭源接入 | ⭐⭐⭐ 「一个 key 代理多家模型 + 统一 /models 清单」正是 ArcBench 这种模式；**但我们是自建、私有化、可离线** |
| **OpenWebUI** | 前端 + 后端 | 界面里填 OpenAI 兼容连接（URL/key），多连接并存 | 界面改即时生效 | 只支持 OpenAI 兼容 / Ollama | ⭐⭐⭐⭐ **可视化配置范式**的直接参照：连接列表、切换默认、连通性测试 |
| **Portkey / Helicone** | 可观测网关 + 路由 | 界面/API 配置 provider + 路由规则（fallback / load balance / conditional） | 即时生效 | 网关内置适配器 | ⭐⭐⭐⭐ **路由规则（条件路由、回退链、重试、超时、熔断）**是我们要补齐的能力 |
| **Vercel AI Gateway** | 云网关 | 统一端点 + provider 选择 | 即时 | 内置适配器 | ⭐⭐ 统一端点 + 成本观测可借鉴，云绑定不可取 |
| **LangChain / Spring AI** | 代码库 | 代码里 new 一个 `ChatOpenAI(...)` | 需重启 | 写 Java/Python 类 | ⭐ 反例：**把通道写进代码**正是我们要消除的 |
| **Claude Code / deepseek-harness** | CLI Harness | 环境变量 / 配置 + 少量 provider 预设 | 改环境变量通常需重启会话 | 内置 provider 枚举 | ⭐⭐ 参照其 provider 预设与「按任务选模型」的雏形；但硬编码枚举是我们要超越的点 |
| **agentskills-runtime 现状** | 仓颉 Agent 运行时 | `DEFAULT_PROVIDER_MAP` + match case（**代码**） | **必须重启** | 改宿主 `src/model` 代码 | — |

## 2. 业界做法的共性结论（可直接吸收）

1. **配置即真相**：通道是数据（YAML / DB / 云端清单），代码里只有「如何按协议发请求」的实现。
2. **热重载是标配**：LiteLLM 改 YAML 热重载、OpenWebUI 界面改即时生效——「改配置要重启进程」在 2026 年属于倒退。
3. **一个抽象层 + N 个适配器**：统一 `ChatModel` 接口（对应我们的 `ChatModel`），OpenAI 兼容是默认适配器，其它协议走专用适配器。
4. **路由是一等能力**：不只是「选一个模型」，而是「按条件/成本/健康在多个候选间路由 + 回退链 + 熔断」。
5. **可观测驱动**：记录 provider / model / tokens / 延迟 / 失败率，再反过来指导路由。
6. **连通性测试与模型清单同步**：界面上点一下就知道这个 key 通不通、有哪些模型（OpenWebUI、LiteLLM 都有）。

## 3. 业界没解决 / 我们不照抄的

| 业界做法 | 问题 | 我们的选择 |
|---|---|---|
| 独立网关进程（LiteLLM Proxy / Portkey） | 多一跳网络、多一个要运维的组件；与 runtime 的 Agent / WebMCP 链路割裂，凭据要同步两份 | **内置在 runtime**：注册表是 runtime 自己的一层薄服务，零额外部署；同时兼容「把已有网关当成一个 OpenAI 兼容通道挂进来」 |
| 云托管路由（OpenRouter / Vercel AI Gateway） | 数据出域、供应商锁定、离线不可用 | **本地 / 私有化优先**，DB 或 .env 为真相源，可完全离线 |
| 协议适配器必须写进主程序（LangChain / LiteLLM CustomLLM） | 扩展要动核心代码、要重新编译；第三方无法闭源发布适配器 | **L3 进程隔离轨插件**承载协议适配器：独立进程、可热启停、第三方可闭源发布、崩了不影响宿主 |
| 插件进程自己拿 key（env 传参） | 密钥散落进程环境、轮换要重启、插件崩溃日志可能泄露 | **`host.secret` 宿主集中托管**：插件按需向宿主取凭据，宿主不把密文交给插件进程环境（沿用现有 `host.mcp` 的凭证范式） |
| 能力靠文档声明 | 「这个模型支持 tools 吗」靠猜，实测踩坑（atomgit 首轮带 tools 返 200 空体） | **能力探测自动化**：接入/启用时自动跑「三枪」探测（chat / stream / tools(+vision)），结果写回注册表 |
| 路由只看可用性 | 不看成本、不看能力匹配 | **成本 + 能力 + 健康三维路由**，复用已有 `model_pricing` / `llm_usage_logs` |
| 必须有配置中心 | 配置中心挂了系统就瘫 | **双驱动兜底**：DB 不可用 → 退化为 `.env` 种子（内置 20 通道常量表降级为离线种子），框架仍完备 |

## 4. 差异化定位（超越点）

| # | 差异化 | 说明 |
|---|---|---|
| D1 | **配置驱动 + 插件扩展双轨** | 同一协议的 N 家厂商 = **纯数据**（零代码、零编译、零重启）；私有协议 = **L3 插件**（进程隔离、热插拔、可闭源）。业界通常二选一，我们两者都给且边界清晰 |
| D2 | **与 Agent 运行时原生一体** | 通道切换直接作用于 Agent / WebMCP / 长程任务热路径，不需要外挂网关；会话级、Agent 级、全局级三档作用域 |
| D3 | **能力探测写回注册表** | 自动拉 `{base}/models` + 实测 stream/tools/vision，把「这个通道/模型到底能干什么」变成表里的布尔位，而不是口口相传的文档 |
| D4 | **host.secret 凭证托管** | 插件进程不接触密钥本体；轮换密钥即时生效，不需重启任何进程 |
| D5 | **成本 + 能力 + 健康三维路由 + 回退链** | 与既有计费/用量表打通，可做「按预算选模型」「失败率超阈值自动摘除」 |
| D6 | **影子 / 灰度流量** | 新通道先接 5% 影子流量对比质量与延迟，再全量——业界多为「切了就切了」 |
| D7 | **为 System-1 自动选路预留接口** | 与 `laya-system1-integration` 用例 #3（模型路由）对齐：路由决策点同时支持「规则引擎」和「Laya 打分」两种策略实现 |
| D8 | **双驱动兜底** | 有 DB 用 DB，没 DB 用 .env 种子，没 AI 也能人工可视化切换——契合「无 AI 仍是完备框架」 |

## 5. 关键取舍与风险（研究阶段结论）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 热路径走进程间调用 | L3 插件代理模式每个请求要过 stdio JSON-RPC，长流式有延迟与背压风险 | **默认直通**（OpenAI 兼容走宿主内置适配器，零跨进程开销）；仅私有协议走插件代理；插件代理要求支持流式分帧与超时熔断 |
| 配置地狱 | 通道表字段膨胀、路由规则复杂难调 | 字段分层：`llm_channel`（连接）/ `llm_channel_model`（模型）/ `llm_route_rule`（路由）；规则只做「能力匹配 + 优先级链 + 回退」三类，不做表达式引擎 |
| 运行中切换的一致性问题 | 正在流式的请求用旧通道，新请求用新通道 | 明确**请求边界切换**语义：切换只影响切换之后发起的请求，进行中的会话可「沿用旧实例直到自然结束」或「下轮生效」二选一（可配） |
| 新增插件目录不会自动发现 | `reconcileDesired()` 只在启动编排内调用一次（`cordis_host_manager.cj:198`） | Phase 2 增加**目录发现触发器**（API / 定时 / 事件），或明确「装插件需触发一次 reload（不重启进程）」 |
| 密钥落库 | DB 里存明文 key 有泄露风险 | 密文存储 + `SecretRef`（`env:` / `vault:` 引用）两种模式，界面永远只回显掩码 |

## 6. 调研结论

**方案可行，且本项目具备做好的独特条件**：已有 `config` 表与按 key 读写 API、已有前端配置页分组、已有事件总线、已有宿主服务代理与凭证托管范式、已有计费与用量表、已有 L3 进程隔离轨插件体系（含 long-running-task 等实战插件）。

要新建的只有三样东西：**通道注册表（数据 + 服务）**、**热生效链路（版本戳 → 重建实例）**、**通道管理 UI 与 API**。协议适配器绝大多数情况不用写（OpenAI 兼容直通），需要写时以 L3 插件形态交付、不碰宿主编译图。
