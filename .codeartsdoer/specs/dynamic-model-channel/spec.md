# 动态大模型通道：需求规格

**版本**：v1.0.0
**创建日期**：2026-10-02
**状态**：待评审 / 待设计落地
**关联模块**：agentskills-runtime（`magic.model`）、web-admin、L3 插件体系
**前置文档**：`problem-analysis.md`、`research.md`

---

## 1. 组件定位

### 1.1 核心职责

把「支持哪些大模型通道、当前使用哪个通道、如何选路、如何兜底」从**编译期代码**迁移为**运行时数据**，并提供可视化管理界面与 API，使通道的增删改切**不需要重启 runtime**；协议适配器以 L3 进程隔离轨技能插件形态扩展，不进宿主编译图。

### 1.2 核心输入

1. 管理员在 web-admin 的通道管理操作（新增 / 编辑 / 启停 / 设为默认 / 测试）
2. 通道厂商的模型清单（`GET {base}/models`）与能力探测结果
3. 运行时健康数据（失败率、延迟、错误码）与用量/计费数据
4. 路由规则（全局 / Agent 级 / 任务级）
5. `.env` 引导配置与内置种子（首次启动与 DB 不可用时的兜底）

### 1.3 核心输出

1. 运行时通道注册表（供 `ModelManager` 查询）
2. 按请求构造（或复用）的 `ChatModel` / `EmbeddingModel` / `ImageModel` 实例
3. 通道列表 / 详情 / 探测结果 / 健康状态 / 变更审计（API + 界面）
4. 通道变更事件（供事件总线广播与插件侧感知）

### 1.4 职责边界

**负责**：通道元数据的存储与版本管理；运行时热加载与实例重建；能力探测与模型清单同步；路由与回退决策；凭证的安全托管与注入；变更审计。

**不负责**：
- 不重写协议实现（`src/model/openai/*` 等确定性代码保持不变）
- 不替代 `config` 表的通用配置职责（通道配置独立建表，避免 config 表语义膨胀）
- 不实现计费结算（复用 `model_pricing` / `llm_usage_logs`）
- 不实现 System-1 打分选路本体（预留策略接口，由 `laya-system1-integration` 后续接入）

## 2. 领域术语

**通道（Channel / Provider）**
: 一个可调用的大模型服务端点，由 `protocol + base_url + credential + 模型清单` 定义，如 `arcbench`、`deepseek`、`ollama`。注册表里的一条记录。

**协议适配器（Protocol Adapter）**
: 把某类协议翻译为 runtime `ChatModel` 接口的实现。分两类：**内置适配器**（OpenAI Chat Completions 兼容，随宿主发布）与**插件适配器**（L3 进程轨插件，独立 exe）。

**模型条目（ChannelModel）**
: 通道下的一个具体模型 ID（如 `deepseek-v4-flash`）及其能力位、上下文长度、价格引用。**以该通道自报的登记名为准，不做任何改名。**

**通道注册表（ChannelRegistry）**
: 运行时持有的通道/模型数据集合，带版本戳（revision），支持热刷新与原子替换。

**热生效（Hot Apply）**
: 配置变更在不重启进程的前提下，于**请求边界**生效（新请求用新配置，进行中请求不受影响）。

**能力探测（Capability Probe）**
: 对通道下的模型自动执行「三枪」实测：纯聊天 / 流式 / 工具调用（按需加视觉），把结果写回能力位。

**路由规则（RouteRule）**
: 决定「这个请求用哪个通道的哪个模型」的规则，支持作用域（全局 / Agent / 任务）、能力要求、优先级链与回退链。

**凭证引用（SecretRef）**
: 密钥的存储定位方式：`env:<VAR>`（引用进程环境或 .env）、`db:<id>`（注册表密文）、`vault:<path>`（外部密钥库）。**插件进程不直接持有密文。**

**影子流量（Shadow Traffic）**
: 新通道以小比例复制真实请求进行质量/延迟对比，不影响主链路结果，用于灰度上线。

## 3. 角色与边界

| 角色 | 诉求 | 交互 |
|---|---|---|
| 系统管理员 | 可视化增删通道、切默认、测连通、看健康 | web-admin 通道管理页 |
| 运维 | 批量导入通道、脚本化切换（CI/现场演示） | REST API / CLI（后续） |
| 开发者 | 新增私有协议通道不改宿主代码 | L3 插件 + `plugin.yaml` |
| Agent（AI） | 按任务自主选通道；通道不可用时自主降级 | Agent 工具 / MCP 工具 |
| 终端用户 | 在聊天框下拉中自助切换具体大模型通道（REQ-DMC-021）；切换不中断会话 | web 聊天框通道选择器（参考 `chatComponent.png`） |

## 4. 功能需求

### REQ-DMC-001 通道注册表（数据源）
通道与模型的定义必须是**运行时可读的数据**，不再是 `DEFAULT_PROVIDER_MAP` 常量。注册表至少包含：通道编码、显示名、协议类型、base_url、凭证引用、启用状态、优先级、作用域、能力位、健康状态、版本戳。

### REQ-DMC-002 种子与引导
首次启动（表不存在或为空）时，将内置常量表（现有 20 个 provider）作为**种子**写入注册表；此后以注册表为准。`.env` 中的 `MODEL_CONFIG` 若与注册表不一致，按「显式覆盖」策略生效并记审计（逃生舱）。

### REQ-DMC-003 热生效（核心）
修改通道配置或切换默认通道后，**不重启 runtime**：注册表版本戳自增 → 广播变更 → `ModelManager` 以新配置构造实例并替换缓存。**验收：切默认通道后 5 秒内新请求走新通道，进程 PID 与 uptime 不变。**

### REQ-DMC-004 请求边界语义
切换只影响切换之后**新发起**的请求。进行中的流式会话按策略（可配）：`drain`（沿用旧实例直到本轮结束，默认）或 `immediate`（下一段生成即切换）。

### REQ-DMC-005 零代码新增同协议通道
新增一个 OpenAI 兼容厂商（如再来一个 ArcBench 这样的网关）必须做到：**只填表单 + 保存**，不改任何 `.cj` 文件、不编译、不重启。

### REQ-DMC-006 协议适配器插件化
私有协议 / 特殊实现（如 tokendance、本地推理、自建网关）以 **L3 进程隔离轨技能插件**形态交付：`skills/<name>/plugin.yaml`（`mode: process`）+ 独立 exe；宿主通过 stdio JSON-RPC 调用宿主侧注册的适配器。插件崩溃不影响宿主，支持自愈重启。

### REQ-DMC-007 凭证托管（`host.secret`）
通道密钥由宿主集中托管：DB 密文存储或 `env:` 引用；界面只回显掩码；插件进程**不通过命令行参数/环境变量接收密文**，改为运行时经宿主服务按需取用（沿用 `host.mcp` 的凭证范式）。密钥轮换即时生效、无需重启。

### REQ-DMC-008 能力探测
保存/启用通道时可一键探测：自动 `GET {base}/models` 拉清单，并对选定模型实测 **chat / stream / tools**（可选 vision）三枪，把结果写入能力位；失败项给出具体错误（如 `provider_not_selected`、200 空体）而非笼统「不可用」。

### REQ-DMC-009 模型清单同步
支持手动/定时同步通道模型清单，新增模型默认「待启用」，避免网关悄悄上线新模型导致误调用。

### REQ-DMC-010 路由规则
支持三档作用域：`global` / `agent:<id>` / `task:<type>`；每条规则声明能力要求（`tools|vision|reasoning|stream`）、候选通道优先级链、回退链。规则冲突时以「作用域更具体者优先」。

### REQ-DMC-011 健康探测与熔断
周期性（可配，默认 60s）轻量探活；连续失败/错误率超阈值自动摘除并切回退链；恢复后自动（或经人工确认）归位。健康状态可视化。

### REQ-DMC-012 成本感知
路由可参考 `model_pricing` 与 `llm_usage_logs`，支持「按预算优先」策略与超限告警（Phase 2+，接口先预留）。

### REQ-DMC-013 可视化管理（web-admin）
新建「大模型通道」页面，至少包含：通道列表（含状态/默认标记/健康）、新增/编辑表单（协议、URL、密钥掩码、作用域）、**一键设为默认**、连通性测试与探测结果展示、模型清单与启停、变更记录。表单按协议动态渲染字段。

### REQ-DMC-014 变更审计
每次通道变更记录：操作者、时间、前后值（密钥掩码）、来源（界面/API/Agent），可回溯。

### REQ-DMC-015 灰度与影子
支持新通道以可配比例接影子流量，对比延迟与失败率，界面展示对比结果，通过后再设为默认（Phase 3）。

### REQ-DMC-016 Agent 工具与 API
暴露 Agent 可用工具（对齐既有的 `plugin_activate` 等工具范式）：`llm_channel_list` / `llm_channel_test` / `llm_channel_switch` / `llm_channel_probe`，使 AI 可自主切换与降级；同时提供等价 REST API。

### REQ-DMC-017 逃生舱与退化
- `.env` 的 `MODEL_CONFIG` 永远可覆盖注册表（显式优先），便于现场救急；
- DB 不可用时，注册表退化为「内置种子 + .env」，**runtime 仍具备完整聊天能力**（双驱动：无 DB 仍完备）；
- 全部通道不可用时，启动阶段**不得**因模型创建失败而跳过 chat 路由注册（改变现状 `main.cj:582-604` 的行为），应注册并在请求时返回明确错误，保证后续热修复生效。

### REQ-DMC-018 非功能要求
| 项 | 要求 |
|---|---|
| 热生效时延 | 配置保存 → 新请求生效 ≤ 5s（默认 2s 内广播） |
| 配置读取开销 | 热路径上不得每次请求查库；注册表内存缓存 + 版本戳比对（版本未变零查询） |
| 直通模式开销 | OpenAI 兼容直通相对现状增加开销 ≤ 1ms（仅多一次注册表查表） |
| 插件代理模式 | 首字节延迟增加 ≤ 50ms（本地 stdio），支持流式分帧，超时可熔断 |
| 并发 | 注册表读多写少，读锁无阻塞；切换用原子替换（copy-on-write） |
| 可用性 | 通道切换/探测失败不影响主链路；注册表服务自身故障退化为内存快照 |

### REQ-DMC-019 安全
- 密钥：DB 密文 + 掩码回显 + `SecretRef`；界面禁止明文展示（沿用 config 表 `is_sensitive` 语义）
- 权限：通道管理接口纳入 RBAC；Agent 自动切换需受「允许自动切换」开关约束
- 插件：L3 插件走既有 `tableWhitelist` 白名单机制，通道表只对通道插件开放
- 审计：密钥变更单独记录（不含明文）

### REQ-DMC-020 兼容与迁移
- 保留 `parseModel` 的严格语义：`provider:modelName` 必须显式写，程序**不补前缀、不猜通道、不改写模型 ID**（2026-10-01 定）；provider 的合法集合改为查注册表
- `DEFAULT_PROVIDER_MAP` 退化为「内置种子」，不再承担运行时真相
- 现有 `.env` 三件套（`MODEL_PROVIDER/NAME/CONFIG`）继续可读，作为引导与覆盖
- `ModelController.cj` 的硬编码 `providerNames` 改为读注册表（消除第三处硬编码）

### REQ-DMC-021 用户端聊天框通道切换器（Phase 1，参考 `chatComponent.png`）
普通用户（非管理员）在 web 聊天界面即可切换大模型通道，无需管理员权限、不经通道管理页：

- **入口**：聊天输入框右下角显示当前通道按钮，点击弹出通道下拉列表（产品参考截图 `chatComponent.png`）。
- **目录内容**：仅 `status=enabled` 且 `scopes` 含 `"user"` 的通道，展示显示名 / 图标 / 能力标签 / 当前选中标记；可附定价倍率与运营标签（如「夜间免费」，数据源 `model_pricing` / 运营配置，可为空）。
- **切换语义**：用户选择随**下一条聊天请求**显式传给 `webmcp/mcp`（`model: "<channel>:<modelId>"`，保持严格 `provider:model` 语义、不猜通道），在请求边界生效；进行中流式会话沿用 REQ-DMC-004 的 drain 语义。前端记住用户上次选择，新会话默认沿用。
- **权限与数据边界**：走独立的**只读目录 API**（不含 base_url / secret_ref / 健康等管理字段），普通用户角色可读；**不经** `llm_channel` 管理 API（那是管理员控制面，见 design §1 对接边界）。
- **范围边界（重要）**：本需求**只支持切换具体大模型通道**。「快速 / 均衡 / 极致」这类**组合通道**（把多个具体通道按场景打包成一档的预设路由）不在本 spec 范围，归 `laya-system1-integration` 关联工程后续实现（见 design §12）。

## 5. 最小可用范围（MVP，Phase 0）

必须一次性交付才算「解决重启问题」：

1. 通道表 + 模型表 + 种子写入（REQ-001/002）
2. 注册表服务与版本戳热刷新（REQ-003）
3. `ModelManager` 改为「查注册表构造实例」，OpenAI 兼容通道直通（REQ-005）
4. 切换默认通道 API（REQ-016 的 API 部分）
5. 请求边界语义（REQ-004，默认 drain）
6. 启动不再因模型失败而阉割路由（REQ-017 第三条）

Phase 1 补可视化、探测与**用户端聊天框通道切换器**（REQ-021），Phase 2 补插件轨与路由/健康，Phase 3 补自动选路与灰度。

## 6. 验收口径（可测）

| 验收项 | 判定 |
|---|---|
| V1 热切换 | 后台把默认通道从 A 切到 B，**不重启进程**，新会话日志出现 `Using chat model: B:xxx`，`uptime` 不归零 |
| V2 零代码新增 | 新增一个 OpenAI 兼容网关通道，全程未改动任何 `.cj` 文件、未执行 `cjpm build` |
| V3 失败可修复 | 故意填错 key → 启动仍注册 chat 路由；热修正 key 后，不重启即可成功聊天 |
| V4 进行中会话不受影响 | 切换时正在流式的会话在 drain 策略下正常完成 |
| V5 密钥不泄露 | 界面与 API 返回中密钥均为掩码；插件进程命令行/环境无密文 |
| V6 严格语义保持 | 裸模型名（无 `provider:`）仍直接报错，不自动推断通道 |
| V7 离线退化 | 断开 DB，runtime 仍能以内建种子 + .env 正常聊天 |
| V8 用户端聊天框切换 | 普通用户（无管理权限）在聊天框把通道从 A 切到 B，下一条消息日志出现 `Using chat model: B:xxx`；目录中不出现 disabled / 非 user 通道；目录与响应无密钥、无 base_url 字段 |
