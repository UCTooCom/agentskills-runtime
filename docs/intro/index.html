技能是怎么被唤起的
  • 技能原文打包注入：前端 src/skills/ 下的每个技能目录（uctoo-operator、 entity-operator、crontab-operator、tiny-pro-operator、 code-generation、data-analysis、document-writing） 都通过 import.meta.glob(..., '?raw') 以原文形式导入并传给助手窗， 再由框架抽取每个 SKILL.md 的元数据，拼成一段「可用技能」清单放进系统提示词。
  • 自然语言触发，按需加载：每个技能都用 SKILL.md 的 description 写清楚自己的触发场景—— 例如 uctoo-operator 写的是「当用户需要操作后台管理系统的任何功能（菜单、权限、角色、用户、 Entity、Crontab）时触发」。你用大白话提需求，模型据此判断该用哪个技能， 再调用 get_skill_content 按需把该技能的正文加载进来。 这样做的好处是：不必一上来就把七个技能的全文全塞进上下文，用到哪一个才读哪一个。
  • 服务端另有一层自动匹配兜底：runtime 侧的 SkillAutoInjector 用 TaskMatcher 对你的任务描述与技能描述做相似度计算，超过阈值才注入，并限制最多注入数量； 匹配策略支持关键词 / 语义 / 混合三种。中文不是按空格分词，而是切成字符二元组， 所以「帮我看看定时任务」这类话也能对上 crontab-operator。
    （注：其中「语义」策略依赖的 embedding / LLM 通道尚未接入， 当前会自动降级为关键词匹配——能力位已经在框架里，等通道接上即可生效。）
  • 技能驱动的不是回答，是操作：这些技能真正厉害的地方在于，它们记录的是 如何调用 WebMCP 工具去操作真实界面——先用 navigate_url 跳到对应页面， 再用 page-agent-tool 读取当前界面状态，然后像真人一样 click 按钮、 fill 表单、select 下拉、翻页。 配合第 4 章里那些自动生成的数据表格页（每页自带的增删改查工具）， 一句自然语言就能落到一次真实的业务操作上。
  • 人格与规则不写死在前端：助手的系统提示词不硬编码在代码里， 而是从数据库 agents 表中 MainAgent 的 system_prompt 读取。 前端刻意留了这样一条原则——配置即事实，没配就是没配，不塞一份用户改不掉的兜底文案。 想改助手的性格与约束，去后台改配置，不必动代码。
多格式文件解析与 L3 进程隔离轨插件
  • 解析能力不在宿主里，而在 L3 插件里：上面对话窗能上传 pdf / ppt / doc / xls / txt / md / csv / json 等一众文档， 它们的多类型文件格式解析，是通过 L3 进程隔离轨插件实现的。每个解析插件跑在独立子进程中， 经 JSON-RPC over stdio 与宿主通信；这也正是 ASR「三维一体」插件约定（plugin.yaml + SKILL.md + scripts/ 同目录）的落点—— 插件既能提供 RPC 服务，又能自动注册成技能、教 Agent 怎么用。
  • 为什么是进程隔离：参照我们此前所做的 《Agent 框架插件机制横向对比研究报告》 （横向对比 deepseek-harness / openclaw / hermes-agent / ASR），ASR 是四家里唯一把「第三方插件默认生成为独立进程工程」的框架—— plugingen 生成的插件缺省就是 --mode process（L3 进程隔离轨）， 产物是独立 cjpm 可执行文件，可脱离宿主单独编译。这带来几个实打实的好处：
    • 崩溃隔离与自愈：Process 轨下只有插件进程会崩，不会拖垮宿主主网关； 并在代码层预留 autoRestart 自动拉起，单插件故障不影响整体服务 （重启风暴防护等可观测性仍在按报告的建议补齐）。
    • 灵活可拓展：想支持一种新的文件格式，只需新增一个插件，不进宿主编译图 （存量宿主模块冻结、只减不增）；插件零 magic 包依赖、独立编译，改完等约 60 秒周期调谐或调 plugin_refresh 即生效，免重启。
    • 安全边界：插件按表级白名单（tableWhitelist）默认拒绝访问数据库， 进程外运行天然收敛了故障与越权的影响面；需要出网或取密钥时，凭证经 host.secret 按引用名代取， 进程内不落明文（与上文 API Key 加密一脉相承）。
  • 差距与共建邀请：坦率讲，目前 ASR 还没有内置多种文件格式的解析插件。 除 PDF / DOCX / PPTX / XLSX 等通用格式会由 ASR 官方以「内置通用解析插件」形式逐步补齐外， 我们诚挚欢迎开发者基于 L3 轨合作共建技能插件生态。 更值得一提的是：得益于仓颉编程语言「二进制发布」的特性（插件是独立可执行文件，可直接分发、也可闭源）， 具备独特业务价值的解析插件，后续可以在技能市场付费销售——把你的能力沉淀成可交易的资产。

PC 客户端：一键安装的桌面智能体

把完整的本地智能体栈（runtime 后端 + web-admin 控制台 + 内嵌 PostgreSQL）打包成一个桌面应用，让普通用户无需搭环境、一行命令都不用敲，就能在本地跑起来。本章介绍 PC 客户端的定位、背后的安装器流水线，以及客户端各界面的功能。

PC 客户端定位
  • 一键安装、降低门槛：将 runtime、web-admin、内嵌数据库与第三方依赖整体打包，由安装向导引导完成，用户拿到的是开箱即用的本地智能体桌面应用，大幅降低使用门槛。
  • 与开源项目完全一致：PC 客户端内嵌的应用，与独立的 agentskills-runtime 与 web-admin 开源项目完全一致——不是裁剪版、也不是另一套实现；PC 只是把它们封装进一个 Electron 外壳并托管其进程。
  • 标准化发布安装流水线：PC 客户端与 runtime 中的原生安装器 ucInstaller 对接集成，形成了一套标准化、可复用的仓颉应用发布安装流水线。工程设计与职责划分详见仓库内的 specs/PcClientInstallProvisioning 与 specs/PcClientInstallerIntegration。

安装器（ucInstaller）的主要功能
  • 集成 runtime 运行所需的数据库：内置内嵌 PostgreSQL 的初始化与启停（initdb、空集群准备），并支持切换为外部 PostgreSQL；安装期只备好空壳，首次运行时再按用户录入自助建库、建号、初始化。
  • 集成运行时所需的第三方库与资源：随安装包分发 runtime 发行包（含 ucInstaller 自身）、OpenSSL 等第三方库与 web-admin 前端资源，统一解压落盘到用户机器，消除手工复制带来的版本漂移；安装包与 runtime 发行包之间以 SHA256 校验保证同源。
  • 从数据库提取种子数据：提供 db export / seed apply / seed verify 等子命令，将 sql/uctooDB.sql 的 schema 与 sql/seed/*.json 的种子数据（公司、任务、角色、权限、菜单等）导入内嵌库；首次运行还会以用户创建的管理员账号为 principal，完成权限与菜单的绑定。
  • 管理员账号创建与密码安全：首次启动的设置页让用户输入 email / 账号名 / 昵称 / 密码，安装器现场计算 bcrypt 哈希落库；密码明文仅经 stdin 瞬时传入、哈希后即丢弃，绝不写入日志或磁盘明文。
  • 可观测的安装过程：安装与初始化以 NDJSON 流式进度回传（--progress=ndjson），失败按退出码（0 成功 / 2 参数错误 / 6 需人工介入）如实呈现，不静默降级为「成功」。
