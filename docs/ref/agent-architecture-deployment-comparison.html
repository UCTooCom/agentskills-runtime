1. 评估方法与公平性声明

1.1 本报告回答的核心问题

上一轮研究中，我们确认了 AGENTS.md 在 ASR 中不是热加载的——这引出一个更上层的架构定位问题： ASR 是作为长期运行的后端服务（类 Spring Boot 企业级框架）设计的，web-admin 与 PC 客户端通过 API/CLI 调用 runtime； 而业界其他智能体项目，究竟是客户端架构还是服务端架构？是否支持像 ASR 一样 配置独立域名 + SSL 证书、部署到云服务器、让 web/PC 客户端远程连接 runtime 端？

1.2 证据等级

B · 文档确证官方 README / 部署文档 / 社区报告明确陈述Claude Code / OpenClaw / Hermes / DSH 的架构与部署形态

重要前提：Claude Code / OpenClaw / Hermes / DSH 四家的内部实现我无法逐行读源码实证 （除 DSH 的 dsh web 绑定地址等少量可从文档确认的点），其架构/部署结论均基于公开文档与社区报告的 B 级证据； ASR 部分则有 A 级源码实证。结论以「是否服务端、能否自托管部署」为判定主轴的，差异足够显著，不依赖字节级精度。

  • CC = Claude Code；OC = OpenClaw；HM = Hermes Agent；DSH = DeepSeek Harness；ASR = agentskills-runtime。

4. 分维度深度剖析

4.1 A1 架构范式：四种形态，一条光谱

把五个项目排在「客户端 ←→ 服务端」光谱上：

  • Claude Code（极左·纯客户端）：agent 循环、工具执行、上下文全在用户本地机器的一个 Node 进程里。所谓「云」，是 Anthropic 托管的临时 VM——用完即弃、闲置回收，不是你能部署、配域名、长期运行的服务端。
  • OpenClaw / Hermes / DSH（中段·服务端守护）：三者都把核心逻辑放进一个长驻守护进程，对外暴露 HTTP/WS API 与 Web UI。差异只在「默认绑定地址」与「是否内建多租户」。
  • ASR（极右·企业级 B/S）：runtime 从第一天就被设计成可独立部署的后端服务，web-admin 与 PC 客户端是一等公民客户端，后端连接地址有完整的四级来源链（见 §7）。

4.2 A4 域名 + SSL：真正的分水岭

这是本报告最关键的一维。OC / HM / DSH 三家虽然「能部署到云」，却都默认 loopback / 私有绑定，把「公网域名 + SSL」当作「你自己架反向代理（nginx/Caddy）」的事，而非 runtime 的内置配置项：

  • OpenClaw：默认 127.0.0.1:18789，远程访问走 Tailscale/VPN/SSH 隧道；WS 可选 TLS。
  • Hermes：网关私有绑定，文档明确「别把 8642 暴露公网，用反向代理 + 认证」。
  • DSH：发布的 dsh web 绑 127.0.0.1:3080；Service Mode 的 HTTP/gRPC 多租户是设计文档描述，域名/SSL 归你的反代。
ASR 的不同：后端地址四级链 __APP_ENV__（宿主注入，PC 取 config.json.backend.url）> localStorage > VITE_BACKEND_URL > 127.0.0.1:8080， WS/MCP/AgentRoot 一律由 API 根派生。这意味着「runtime 部署到云、配独立域名、多客户端远程连」是架构起点， 不是 DIY 附加项——PC 端改一个 config.json.backend.url 即切到公网 runtime，本机回环 https 还会强制降 http。

4.3 A6 多租户：DSH 与 ASR 领先，其余偏单操作员

Claude Code 是单用户本地；OpenClaw 自我定位「personal assistant，不是 multi-tenant system」；Hermes 个人向、靠 OpenShift 文章才显企业野心。 DSH 的 Service Mode 在设计文档里就给了多租户、资源配额、凭证隔离的 K8s 部署形态； ASR 则通过 RBAC 两层（API 层 RequirePermissionMiddleware 超管持 *、菜单层 getUserMenuTree） 实现多用户隔离—— 两者在「多租户」这一维上最接近企业级，但 ASR 是源码实证，DSH 是设计文档描述。

5. Claude Code：唯一的纯客户端 outlier

结论先行：Claude Code 不是服务端架构。它不满足你描述的任何一种「服务端」诉求——不能自托管、不能配自己的域名、不能让远程客户端连接你自己的 runtime。

具体拆解：

  • 执行位置：agent 循环与工具（文件读写、命令执行）全部在本地机器执行。它不是一个「把请求发给远端服务端」的瘦客户端，它自身就是运行时。
  • 所谓「云能力」：Anthropic 提供的是临时 VM 云会话（ephemeral），用于在无本地环境的场景跑 agent，闲置即回收，不是你持久部署的服务端。
  • Remote Control 特性：这是出站镜像——把本地 CLI 的状态同步到一个 Web 界面便于查看，不开入站端口，经 Anthropic API rendezvous 中转。它不是「web 客户端连接你的 runtime」。
  • 自托管服务端：Claude Code 没有「部署你自己的 Claude Code 服务端 + 配域名」这种模式。Anthropic 另提供 Agent SDK / 平台能力，但那不是「自托管 Claude Code runtime」。

这反而衬托出 ASR 的站位价值：当别人把 agent 当「本地工具」或「托管在厂商云里的临时算力」时，ASR 把它当你能拥有、能部署、能配域名的企业后端。

6. 服务端三家（OC / HM / DSH）的真实边界

OpenClaw、Hermes、DSH 三家都「服务端化」了，但存在两个共性边界，理解它们才能看清 ASR 的差异化空间：

6.1 边界一：默认 loopback，域名/SSL 交给用户反代

三家都把「暴露到公网 + 配域名 + 挂 SSL」视为运维层的 DIY 动作，runtime 自身不提供「填域名、传证书即生效」的一等配置。对单操作员/个人助理足够，但对「开箱即用的企业部署」是一道额外门槛。

6.2 边界二：产品定位偏单操作员，多租户非默认

OpenClaw 公开声明「not a multi-tenant system」；Hermes 是个人向、靠外部文章才显企业野心；DSH 的 Service Mode 多租户在设计文档而非默认体验里。换言之，它们的「服务端」更接近「一个人远程连自己机器上的守护进程」，而非「多用户共享的企业后端」。

一个佐证 ASR 理论基座的点：DSH 的核心理念恰恰是 「runtime becomes the product / runtime as a Service」（mech.app 社论），其文档直接给了多租户、资源配额、凭证隔离的 K8s 形态。 ASR 与 DSH 在哲学血统上一致（你也早把 DSH 定为理论基石），区别是 DSH 发布的默认体验仍是 127.0.0.1:3080 的本地 WebUI， 而 ASR 从第一天就把「云端部署 + 多客户端」做成了主路径。

7. ASR 的企业级 B/S 站位（源码实证）

ASR 的架构不是「客户端框架顺手加了服务端」，而是服务端优先。以下均为 A 级源码实证：

7.1 runtime 即长驻后端

src/app/main.cj 启动期实例化 AgentLoadManager 并 loadFromDirs，把 runtime 作为长期运行的后端服务加载——这与 Spring Boot 把应用作为常驻服务的范式一致，而非 CLI 一次性执行。

7.2 后端地址四级链（多客户端连接的基础）

apps/web-admin/src/utils/runtime-config.ts 定义了 ASR 区分于其他框架的关键设计：

后端地址唯一真相源四级优先级：
  ① __APP_ENV__  （宿主注入，PC 端取 config.json.backend.url）
  ② localStorage  uctoo.backend_url   （web 登录页「服务端」入口）
  ③ 构建期 VITE_BACKEND_URL
  ④ http://127.0.0.1:8080            （内嵌默认）
WS / MCP / AgentRoot 一律由 API 根派生，禁止再配独立 URL；
本机回环 https 强制降 http。

这条链意味着：web-admin 和 PC 客户端都是 runtime 的一等客户端，它们连接哪个 runtime（本地 / 局域网 / 公网云）完全由一处配置决定。换公网部署 = 改 config.json.backend.url，无需改代码。

7.3 持久化与权限分层（企业特征）

  • 持久化：PostgreSQL 承载 db_info、权限、会话、种子数据；installer 的 db export/import 流水线把 schema + 种子纳入可重放的工程化体系（见 sql/seed/export-policy.json）。
  • 权限分层：API 层 RequirePermissionMiddleware（超管持 *）+ 菜单层 getUserMenuTree（缺 permissions 看不到入口非 403），构成 RBAC 两层隔离。
  • 多客户端一致：L3 插件经 stdio JSON-RPC 与 runtime 通信，宿主与插件解耦，远端部署不影响插件隔离模型。

9. 对 GOAI 参赛叙事的战略含义

把上面的结论翻译成参赛材料里可直接用的论据：

9.1 差异化卖点（建议单列）

  • 「Deployable Multi-Client Agent Runtime」：runtime 即企业级可部署后端，web / PC / 任意 HTTP 客户端都是一等公民——这不是大多数 agent 框架的默认形态。
  • 「Domain + SSL as First-Class Config」：区别于 OpenClaw/Hermes/DSH 的「反代 DIY」，ASR 的后端地址链让「配域名、挂证书、切公网」成为改一处配置即可生效的内置能力。
  • 「Runtime as a Service，not a local tool」：与 DSH 哲学同源（runtime becomes the product），但 ASR 把云端多客户端做成了主路径而非设计文档里的愿景。

9.2 竞品定位话术

项目一句话定位对 ASR 的关系
Claude Code本地 CLI 工具 / 厂商托管临时算力非服务端，不构成本赛道竞品（错位）
OpenClaw个人助理式网关守护服务端但单操作员；ASR 在企业多客户端上更彻底
HermesPython 服务端守护 + 记忆层服务端但偏个人向；ASR 有原生 RBAC 分层
DSHHarness + Service Mode 多租户理论基石同源；ASR 把云端部署做成默认体验
ASR企业级 B/S 多客户端 runtime差异化站位：可部署 + 配域 + 多客户端是架构起点
诚实边界（避免被评委挑战）：
  • ASR 的「多租户」目前是单部署多用户 RBAC 隔离，尚未到 DSH 设计文档里「独立资源配额/凭证隔离」的硬多租户粒度——参赛时描述为「multi-user RBAC」比「multi-tenant」更严谨。
  • OC/HM/DSH 的部署能力为文档级证据，若评委深挖其内部实现，应明确「以官方部署文档为准」，不要编造源码细节。
  • Claude Code 的「非服务端」结论不影响其作为最强 agent 能力标杆——本报告的判据是「架构/部署形态」，不评价 agent 智力水平。
