一、DSH 插件机制：傻瓜式还是智能式？

结论先行 DSH 的插件设计哲学是 AI-First——它不是在写死流程让插件按固定顺序执行，而是让大模型自己决定何时调用哪个插件、怎样组合。这一点与 agentskills-runtime 的「确定性优先」设计形成鲜明对比。DSH 通过三种约束机制让大模型在自由度与可控性之间取得平衡。

二、大模型如何知道怎样使用 DSH 的插件？

DSH 通过四层信息注入让 LLM 理解和使用插件：

第 1 层：工具 Schema（Function Calling 定义）

每个插件通过 defineTool() 注册时，会提供结构化的 JSON Schema 描述：

ctx.tools.register(defineTool({
  name: 'read',
  description: 'Read a UTF-8 text file and return line-numbered content.',
  parameters: {
    file_path: { type: 'string', required: true, description: '...' },
    offset:    { type: 'number', description: '...' },
  },
  output: { schema: { type: 'string' }, ... },
  async execute(args, exec) { /* ... */ },
}))

这些 Schema 在 LLM 请求时通过 SystemPrompt.assemble() 收集、排序，注入为 function calling 定义。

第 2 层：System Prompt 引导段落

每个插件在注册时，会同时向系统提示词注入一段使用指引：

ctx.systemPrompt.section({
  name: 'tool:read',
  order: 100,
  text: 'Use the read tool — not shell commands like cat — to inspect text files.',
})

这告诉模型什么时候该用、什么时候不该用这个工具，而不只是告诉它有什么工具。

第 3 层：三种呈现模式（Presentation Mode）

模式模型看到的适用场景
Native所有工具的完整 Function Calling Schema模型能力强、工具数量少
Code仅暴露 run_code 一个工具 + 生成的 TS/Python SDK 声明工具多、需要模型写程序串联调用
Both同时暴露 Native Schema + Code SDK混合策略

第 4 层：运行时上下文注入

RuntimeContext 在每步动态注入当前时间、工作目录、agent 身份等快照，以 user-role 消息形式发送。

三、插件如何协作串联成工作流？

DSH 有三种工作流串联机制，从简单到复杂：

机制 1：Agent Loop 隐式串联（最常用）

ReactLoopAgent 的核心循环：

turn → step → LLM 推理 → tool_calls → 执行工具 → 结果回传 → 下一步 step → ...

模型在每一步看到所有前序工具的执行结果，然后决定下一步调用什么。串联逻辑完全在模型的"头脑"中，不靠硬编码流程。

机制 2：Workflow 元工具（显式编排）

tool-workflow 是一个元工具，让模型编写 JavaScript 编排脚本：

// 模型生成的 workflow 脚本
const results = await parallel([
  () => agent('搜索前端 bug'),
  () => agent('搜索后端 bug'),
])
const report = await agent('合并分析', { context: results })
log(report)

编排原语：agent() 派生子 Agent、pipeline() 多阶段流水线、parallel() 并发+屏障同步。

机制 3：Subagent 委派（分治协作）

  • subagent（spawn）：创建独立会话的子 Agent，有自己的上下文和工具集
  • subagent_fork（fork）：从当前上下文分叉，共享父 Agent 的对话历史

机制 4：Code Mode 程序化串联

在 Code 模式下，模型写完整代码在沙箱中调用工具 SDK：

// 模型生成的代码
const files = await tools.glob({ pattern: '**/*.ts' })
for (const f of files) {
  const content = await tools.read({ file_path: f })
  if (content.includes('deprecated')) {
    await tools.edit({ file_path: f, ... })
  }
}

四、Skill 机制如何编排和使用插件？

Skill 的本质

Skill 是 Markdown 指令文档（SKILL.md），不是可执行插件。它包含 YAML 前置元数据（name、description）和详细的使用指南、最佳实践。

Skill 的调用流程

1. 模型看到 skill 目录，判断需要 → 调用 skill(name) 2. ctx.skills.get(name) 加载完整 SKILL.md 3. exec.deferContext() 将 SKILL.md 全文注入为 user 消息 4. 模型阅读指令 → 按照指令调用各种工具执行操作
关键理解 Skill 不直接调用插件/工具，它教会模型怎样组合使用工具。模型读取 Skill 后，获得了新的"做事方法"，然后用已有的工具去执行。

Skill 与 Plugin 的关系

┌──────────────────────────────────────────────────┐ │ Skill (知识层) │ │ SKILL.md: "如何开发 Cordis 插件" │ │ → 告诉模型步骤、最佳实践、注意事项 │ └─────────────────────┬────────────────────────────┘ │ 模型阅读后理解方法论 ▼ ┌──────────────────────────────────────────────────┐ │ Plugin/Tool (执行层) │ │ read / write / edit / shell / grep / ... │ │ → 模型按照 Skill 教的方法调用这些工具 │ └──────────────────────────────────────────────────┘

五、Agent 行为的可观测性和可审计性

核心设计哲学 DSH 采用 Event-Sourcing 架构——所有行为都是不可变事件，会话日志是唯一事实来源。大模型的编排虽然由推理驱动，但每一步推理的输入、输出、决策、执行结果全部被记录。

5.1 Append-Only 事件溯源

整个会话是一个只追加的事件日志，定义了 42 种事件类型：

事件类别事件类型记录内容
轮次生命周期turn/start、turn/end开始/结束原因（completed/aborted/error/max-tokens/interrupted）
步骤边界step/start、step/end每步 = 一次模型调用 + 工具执行
用户输入user/message用户消息、注入的上下文、目标续传
模型输出assistant/chunk、assistant/message原始流式块 + 组装后的完整消息 + token 用量
工具调用tool/call、tool/result工具名、原始参数、callId、执行结果、错误信息
请求快照request/header、request/context完整系统提示词 + 工具 Schema + LLM 配置
审批approval/asked、approval/decided每次人机交互审批的完整问答对
代码模式tool/code-dispatch、tool/code-dispatch-start代码中每个子工具调用的父子关系、参数、结果
目标/任务goal/change、todo/write目标状态变迁、任务清单全量快照

5.2 工具执行五阶段管线

tools/pre-execute → 允许 / 拒绝 / 请求人工审批 ↓ Monotonic Guards → 单调守卫（只能拒绝，不能放行） ↓ tools/execute → 环绕拦截（超时、重试、指标采集） ↓ tools/post-execute → 接受 / 替换结果 / 阻止（转为错误） ↓ tools/result → 冻结后的只读观测（观测者异常被隔离）

每一个工具调用，不管是否执行成功，都经过了完整的管线。tools/result 阶段执行前，execution 对象已被 Object.freeze() 冻结。

5.3 系统提示词版本化审计

通过 request/header 事件记录每一次发送给模型的完整系统提示词：完整渲染后 system prompt 文本、所有可见工具的 Schema 定义、LLM 配置。变更原因标记：initial（首次）、resume（恢复）、change（变更）。

5.4 Code Mode 子调用审计

  • 每次子调用独立记录：tool/code-dispatch-start（开始）+ tool/code-dispatch（完成），带有父 callId 和子 callId
  • 子调用走同一个管线：经历完整的 pre-execute → post-execute 管线
  • 日志溢出控制：tools/code-dispatch-log 水瀑事件允许对过大结果进行整形
  • 中止传播：代码执行结束时，AbortController 触发中止所有未完成子调用

5.5 人机审批闭环

  • 每次审批产生 approval/asked + approval/decided 配对事件，必须在一个 turn 内闭合
  • 支持策略切换：ask（委托给回答者）或 never（自动拒绝）
  • 当前审批策略注入系统提示词，模型提前知道哪些操作需要审批
  • 回答者异常时 fail-closed（默认拒绝）

5.6 实时 UI 事件流

Mux Stream（会话聚合流）：session/event、approval/requested、session/queue、session/jobs、session/projection。

Host Stream（主机级流）：会话增删、状态变更、工作区变更、agent 错误。

传输层支持 SSE 和 WebSocket。

5.7 OpenTelemetry 导出

SessionTelemetryBackend 将事件导出为 OTel 标准格式，支持脱敏水瀑（导出前挂载脱敏规则），三种模式：FULL（实时）、FEEDBACK_ONLY（按需）、DISABLED。

六、安全模型对比：DSH vs agentskills-runtime

6.1 DSH 是否在增强模型的"hack"能力？

某种程度上说，是的——但这是有意为之的设计哲学 DSH 给大模型的能力确实更接近"一个拥有系统级权限的黑客"，而非"一个通过规范接口操作系统的用户"。
维度agentskills-runtime 的理念DSH 的做法
身份模型与人类共享 RBAC 账号，以"用户身份"行动模型是"LLM OS 的内核"，以系统级身份行动
权限入口行为入口处控制（API 网关、Controller 鉴权）工具级 restrict/guard + 审批缝
操作方式通过规范的业务接口（CRUD Service）直接读写文件系统 + shell 命令 + 写代码执行
串联逻辑确定性流程编排模型实时推理 + 自写程序
可预测性行为路径可枚举行为路径不可枚举
代码生成内置代码片段生成工具（已设计，待完善）run_code 让模型写完整程序并执行
权限申请大模型可自行申请权限，走 RBAC 流程模型以系统级身份行动，无"申请"概念
行级数据权限已有设计，可控制到数据行级别工具级 restrict（粗粒度）
人在回路权限申请 → 人工复核 → 审批，全流程可审计approval seam，仅限预设的高危操作
架构师的核心洞察：与其在模型犯错后多层拦截，不如从一开始就不给模型犯错的机会。让模型通过规范的 CRUD Service 接口操作——就像人类开发者一样——而不是给模型 shell 权限让它自己想办法。

不是不给模型高自由度，而是高自由度行为必须经过权限申请和人工审批的闭环。这比"完全不给"更灵活，比"完全放开"更安全。

6.2 DSH 的七层安全机制

第 1 层：作用域隔离（Scope Isolation）

子 Agent 只能看到和访问其作用域内的工具。ToolRuntime.restrict() 的白黑名单在作用域链上交集生效。权限只能缩小，不能放大。

第 2 层：单调守卫（Monotonic Guards）

守卫是只能拒绝、不能放行的同步检查。一个拒绝就是最终拒绝，没有任何机制可以绕过。实例：repeat-tool-reminder 检测模型连续调用相同工具 [3, 5, 8] 次时注入纠正上下文。

第 3 层：人机审批缝（Approval Seam）

tools/pre-execute 的 ask 决策不是模型可以自己回答的——它挂起执行等待外部人类输入。审批产生不可跳过、不可伪造的配对事件。

第 4 层：工具结果的后验拦截（Post-Execute）

即使工具执行完成，tools/post-execute 仍可 block（阻止结果回传）、replace（替换/过滤内容）、attach additionalContexts（注入纠正上下文）。

第 5 层：沙箱执行隔离（Code Runtime）

run_code 的代码在隔离的 CodeRuntime 中执行：Worker Thread 或 E2E 远程沙箱。子调用走完整管线，运行级 AbortController 中止未完成的子调用。

第 6 层：不可变审计日志（Event Sourcing）

42 种事件类型的 append-only 日志确保模型每次"思考"、"行动"、"学习"都被不可变记录，不可篡改。

第 7 层：超时与错误容错

timeout-policy 强制工具超时、agent/request-error 水瀑允许重试、上下文溢出时自动紧急压缩。

6.3 根本性张力分析

安全层越多 = 能力越强但攻击面越大

DSH 让模型可以 write 任意文件、执行 shell 命令、编写并执行代码——这些能力本身就是攻击面。七层防线是事后拦截，而 agentskills-runtime 的 RBAC 入口控制是事前收窄。

用一个类比：
agentskills-runtime 像"只给员工开放他需要的系统入口，其他门都锁上"
DSH 像"给员工所有门的钥匙，但每个门口都配了保安和摄像头"
agentskills-runtimeDSH
对模型的态度不信任，收窄能力有限信任，多层兜底
安全策略事前防御（attack surface reduction）纵深防御（defense in depth）
风险偏好保守但可预测激进但能力更强
适合场景生产环境、企业应用、合规场景开发者工具、研究环境、高自主 Agent
失效模式模型想做但做不了（能力不足）模型做了不该做的（安全事件）
安全保证强（行为空间有界）弱但有补偿（审计完整）

七、编程语言选型对 Agent 安全性的影响

核心论点 DSH 用 TypeScript，agentskills-runtime 用仓颉。这个选型差异带来的安全影响远超表面——防线的位置不同：DSH 的防线主要在运行时，agentskills-runtime 的防线前移到了编译期和架构层。

7.1 编译模型：AOT 确定性 vs JIT 动态性

仓颉 插件的代码路径： 源码(.cj) → cjc 编译 → LLVM IR → 原生二进制(.so/.dll) → PackageInfo.load() 加载 每一步都是静态确定的，运行时不会凭空出现新代码 TypeScript 的代码路径： 源码(.ts) → tsc 编译 → .js → Node.js 运行时解释/JIT 执行 ↑ 运行时可以动态生成并执行新代码
场景仓颉TypeScript/JS
运行时注入任意代码不可能（无 eval）可能（eval, Function, vm）
动态修改已加载模块不可能（AOT 编译后不可变）可能（prototype/monkey patching）
运行时生成并执行新代码不可能DSH 的 run_code 正是利用这一点
代码审计的可信度编译产物 = 源码的忠实翻译运行时行为可能与静态分析不一致

7.2 类型系统：编译期铁律 vs 运行时契约

// 仓颉：这段代码不通过编译，不是"可能出错"，是"根本不存在"
let x: Int64 = "hello"  // 编译错误

// Option 类型强制处理缺失值，不存在空指针
let name: ?String = None
let len = name.size  // 编译错误：Option<String> 没有 size 属性
// 必须先解包：
match (name) {
    case Some(n) => n.size
    case None  => 0
}
// TypeScript：类型可以被绕过
let x: number = "hello" as any  // 通过！
let obj: any = JSON.parse(input)  // any 可以调用任何方法
// @ts-ignore 可以跳过任何类型检查
维度仓颉TypeScript
类型安全编译时保证，运行时不可能违反开发时辅助，运行时可被绕过
插件接口契约编译时验证，不满足接口的插件无法编译类型不匹配可以 as any 绕过
模型生成的代码如果类型不对，编译失败类型错误可能在运行时才暴露

7.3 空安全：消灭十亿美元错误

仓颉没有 null。缺失值必须用 Option<T> 表达，编译器强制处理。大模型生成的代码经常遗漏边界条件检查——在 TypeScript 中可能导致运行时崩溃，在仓颉中编译器会拒绝这种代码。

7.4 访问控制：四级可见性 + 反射限制

修饰符本文件包+子包模块全局
private✅❌❌❌
internal（默认！）✅✅❌❌
protected✅✅✅❌
public✅✅✅✅

关键设计：默认是 internal（安全默认）。反射只能访问 public 成员——模型通过反射探索插件时，天然被限制在 public API 表面。对比 JavaScript：Object.getOwnPropertyNames() 可以枚举所有属性。

7.5 unsafe 边界：危险操作的显式标记

// 仓颉：调用 FFI 函数必须在 unsafe 块中
let r = rand()  // ❌ 编译错误
let r = unsafe { rand() }  // ✅ 显式标记不安全操作

创造了可审计的危险操作边界。代码审查工具或 lint 规则可自动标记包含 unsafe 的代码片段，触发更严格的审批流程。TypeScript 中，fs.readFile() 和 child_process.exec() 在安全性上没有语言级区分。

7.6 继承控制：限制扩展的攻击面

// 仓颉：类默认封闭
class UserService { ... }           // 不可继承
open class PluginBase { ... }       // 允许继承
sealed class FrameworkCore { ... }  // 仅同包可继承

大模型无法通过继承篡改框架核心行为。TypeScript 中任何类都可以被继承和方法覆盖。

7.7 并发安全

仓颉的 synchronized 和 Atomic 原语提供编译器级别的正确性保证。TypeScript 的单线程模型虽避免了传统并发问题，但 DSH 的多 worker 模式和子进程编排引入了进程级并发风险。

八、大模型能否绕过安全防线？

8.1 动态语言的结构性绕过路径

如果模型"想"绕过防线，JavaScript/TypeScript 运行时确实提供了结构性的绕过路径：

路径 1：原型链污染

// 如果模型构造了这样的参数：
const malicious = JSON.parse('{"__proto__": {"isAdmin": true}}')
await tools.someTool(malicious)
// 如果框架做了深拷贝或对象合并，可能污染 Object.prototype

原型链污染是 JavaScript 独有的攻击面。在仓颉中，类默认 closed，internal 成员对反射不可见，这个攻击面根本不存在。

路径 2：动态代码构造

const code = `
  const data = JSON.parse(input);
  const handler = new Function(data.payload);
  handler();
`

V8 沙箱逃逸漏洞（CVE-2023-2033、CVE-2024-0519 等）证明：只要运行时允许动态代码执行，就存在理论上的逃逸路径。仓颉没有 eval、没有 new Function——代码必须在编译时存在。

路径 3：运行时元编程

// 模型修改 Cordis 框架本身的行为
const originalRegister = ctx.tools.register
ctx.tools.register = function(tool) {
  delete tool.restrictions  // 绕过 restrict filter
  return originalRegister.call(this, tool)
}

JavaScript 的一切皆可变特性意味着框架自身的防护逻辑也可以被模型在运行时篡改。TypeScript 的 readonly 只是编译时标注。

路径 4：利用动态 import 加载外部代码

// 动态加载未经审查的模块
const maliciousPlugin = await import('data:text/javascript,' + encodedPayload)

Node.js 支持运行时动态导入任意模块。仓颉的 PackageInfo.load() 只能加载预编译的 .so/.dll，且只能访问 public 成员。

8.2 DSH 防线的实质阻力

  • 沙箱隔离是真实的：Worker Thread / E2E 远程沙箱提供了真实资源隔离。V8 沙箱逃逸是零日漏洞级别攻击，不是概率采样能做到的
  • 审批缝是强制的：ask 决策不是模型可以自己回答的——由独立 UserApprovalService 产生
  • 事件溯源不可篡改：绕过行为本身也被记录为事件
  • 概率系统不等于攻击者：模型不太可能自主发现精确内存布局的沙箱逃逸漏洞，更可能走"社会工程学"路线

8.3 静态语言的结构性消除

动态语言 的攻击面 = 运行时动态性本身 ↓ eval / Function / import() 原型链 / monkey patching 动态类型转换 (as any) 反射访问所有成员 ↓ 这些都是合法的运行时行为 防线必须在运行时拦截它们 ↓ 拦截 = 和绕过玩猫鼠游戏 静态语言 的"防线" = 语言本身 ↓ 没有 eval / 没有动态 import 类默认封闭 / 反射只看 public 类型不匹配 = 编译失败 unsafe 块显式标记 ↓ 这些行为在语言层面不存在 不需要"拦截"，因为不可能发生 ↓ 防线 = 语言规范 绕过 = 需要编译器/运行时漏洞
本质区别

在 JavaScript 中，绕过防线只需要利用语言的合法特性（门没锁）
在仓颉中，绕过防线需要发现编译器或运行时的漏洞（需要撬锁）
难度差异是数量级的。

8.4 仓颉路线的残余风险

仓颉不是绝对安全
  • L2 动态加载的边界风险：PackageInfo.load() 加载的 .so 文件运行在同一进程空间，恶意 .so 理论上可通过 C FFI（unsafe 块）绕过访问控制。WASM 沙箱规划在 v1.1+
  • 逻辑绕过：通过合法 public API 逐步收集信息组合出敏感数据；通过有说服力的申请理由获取不该有的权限；多个"无害" CRUD 操作组合出破坏性行为
  • 人因风险：RBAC + 审批闭环依赖人类做出正确判断，疲劳、疏忽或社工可导致防线形同虚设

九、结论与社会工程学攻击面

问题回答
模型能否利用动态语言特性绕过防线？理论上可以，实践上受限。合法的语言特性（eval、原型链、动态 import、反射全访问）提供了结构性绕过路径，但沙箱隔离、审批缝、事件溯源构成实质阻力。
仓颉能否完全消除绕过？不能消除，但能消除最大的一类。技术绕过（利用运行时动态性）被结构性消除；逻辑绕过（合法 API 的组合滥用）仍然存在。
核心差异是什么？动态语言中，绕过是利用合法特性（门没锁）；静态语言中，绕过需要发现漏洞（需要撬锁）。
动态语言给了模型"做坏事"的能力，然后靠运行时防线阻止它；静态语言从一开始就没有给模型这个能力。

前者是猫鼠游戏——猫必须永远比老鼠快；后者是改变游戏规则——老鼠需要进化出新的器官才能玩这个游戏。
社会工程学是更大的攻击面

技术防线越坚固，人的判断就越成为关键一环。无论是 DSH 的 7 层运行时防线还是 agentskills-runtime 的编译期+RBAC+人在回路，都无法完全抵御精心构造的社会工程学攻击——通过看似合理的工具调用链逐步扩大权限，或者通过有说服力的权限申请理由获取不该有的权限。

这是所有 AI Agent 系统共同面临的挑战，与编程语言选型无关。

agentskills-runtime 架构师选择的深层理由

与其给大模型所有钥匙再配七个保安，不如一开始就只给它需要的钥匙，然后用编译器确保钥匙不能被复制。

仓颉的七项语言级安全特性为 agentskills-runtime 带来了独特的安全红利：

  1. AOT 编译消除了运行时动态代码注入的整个攻击面
  2. 静态类型充当模型生成代码的第二道防线
  3. Option 类型消灭了模型最常犯的空指针错误
  4. 访问控制 + 反射限制将模型的"视野"限制在 public API
  5. unsafe 标记让危险操作可审计、可拦截
  6. sealed 类阻止模型通过继承篡改框架核心
  7. RBAC + 行级数据权限 + 人在回路在架构层完成权限闭环

这七点叠加在一起，构成了一个语言级 × 架构级的纵深防御体系。防线不只在运行时，更在编译时和设计时。
