1评估方法与公平性声明

1.1 双口径评分体系

单一口径评分容易让"工程投入量大"的项目碾压"设计理念先进但尚未铺开"的项目，反之亦然。本报告采用双口径分离评分，让设计与工程各自说话：

口径衡量什么5 分4 分3 分2 分1 分
设计完备度
(Design)		 机制在设计层面是否自洽、完整、有理论支撑 业界一流，有原创贡献 完整可用，无明显设计缺口 有方案但有缺口 雏形/实验性 缺失
落地成熟度
(Maturity)		 机制在工程层面是否已铺开、有测试、有生态 大规模验证，生态成熟 已上线，有测试有用户 能跑通但缺验证/生态 能 demo 但未铺开 未实现
公平性原则：当某项目在某维度"设计 5 / 成熟 2"时，不代表它比"设计 3 / 成熟 4"的项目差——前者可能是理念领先但尚在早期，后者可能是工程扎实但设计平庸。两个口径分开看，读者自行权衡。

1.2 证据等级

A 级：源码确证（附文件路径 + 行号） B 级：官方文档确证（附文档路径） C 级：基于源码结构的合理推断

5隔离模型专题：四种哲学

四家对"插件与宿主如何隔离"给出了四种截然不同的哲学回答，折射出各自的语言运行时与部署形态约束。

DSH

fiber ctx 隔离

同进程内，每个插件获得独立 fiber ctx，作用域隔离但共享内存。哲学：信任插件，以轻量换性能。

优势：零 IPC 开销，HMR 原生。劣势：恶意插件可逃逸。

OC

Extension Host 进程

独立 Extension Host 进程，API 白名单。哲学：借力平台，信任边界由 VSCode 定义。

优势：成熟可靠，生态丰富。劣势：进程开销，非自研。

HM

in_process / host 双模式

可信插件 in_process，不可信插件 host 子进程。哲学：按信任分级，灵活选择。

优势：兼顾性能与安全。劣势：双模式增加复杂度。

ASR

三轨：内嵌/L2/L3

内嵌轨零开销，L2 动态库同进程独立符号表，L3 进程完全隔离。哲学：按需选轨，隔离强度可调。

优势：设计最强，L3 进程级隔离。劣势：L2 卸载不完善，Sync 轨 51 分钟重编。

ASR 三轨选轨策略：默认 L3 process 轨（plugingen.cj:48 写死 var mode = "process"），以"不动宿主 + 进程隔离"为默认安全姿态。内嵌轨保留给核心插件（零开销），L2 动态库轨作为中间态规划。这一策略以"牺牲内嵌轨热重载"换取"L3 进程隔离 + 宿主冻结"，是静态语言运行时下的务实选择。

双口径解读：ASR 的设计均值 4.1排名第二（仅次于 OC 4.4），但成熟均值 3.3排名末位——这正是"设计先进但早期"的典型画像。D12（自进化）维度 ASR 设计 5 分与 OC 并列第一，但 ASR 的 5 分来自确定性代码生成工具链这一原创贡献，OC 的 5 分来自skill_workshop + 后台自动评审的工程完整度。两者"5 分"的内涵不同。
避免误读：不要把"成熟度低"等同于"差"。ASR 在 D3（隔离）、D7（能力发现）、D12（自进化）三个维度的设计领先，是语言运行时与产品定位决定的结构性优势，会随工程推进转化为成熟度。反之，OC 在 D6（热重载）的设计 3 分是 VSCode 扩展机制的结构性限制，非工程投入可弥补。

8根因解读：为什么它们如此不同

四项目的差异不是偶然，而是三个硬约束的必然结果。理解根因，才能判断哪些差异可借鉴、哪些是结构性代价。

8.1 硬约束一：语言运行时

项目语言运行时特性对插件机制的约束
DSHTypeScriptV8 JIT + 动态类型天然 HMR、fiber 响应式、IoC 容器
OCTypeScriptVSCode Extension Host借力 VSCode 进程隔离与生命周期
HMPythonCPython + GILABC + 装饰器、importlib 动态加载、子进程隔离
ASRCangjie(仓颉)AOT 编译 + 静态类型编译期注解校验、反射、L2 动态库/L3 进程

语言运行时决定了插件机制的天花板：TS/JS 的动态性天然支持 HMR（DSH 5 分），静态语言 AOT 编译天然不支持热重载（ASR 3 分）——这不是设计水平的差距，而是语言物理约束。但静态语言换来了编译期类型安全（ASR D5 编译期注解校验）和进程级隔离（ASR D3 设计 5 分），是不同的 trade-off。

8.2 硬约束二：部署形态

项目部署形态对插件机制的约束
DSHNode.js 服务/CLI单进程多 fiber，信任插件，轻量隔离
OCVSCode 桌面应用Extension Host 进程，借力平台安全边界
HMPython 服务in_process/host 双模式，按信任分级
ASR服务端 + Web + App 多端多端一致要求强隔离 + 确定性生成

ASR 的多端部署形态（服务端 + Web + App）要求UMI 同构（以数据库结构为单一事实源驱动多端一致代码生成），这直接催生了确定性代码生成工具链——而确定性工具链正是 RSI 自进化的"框架之手"。换言之，ASR 的 D12 优势根因在于部署形态，而非单纯的设计选择。

8.3 硬约束三：生态冷启动策略

项目生态策略对成熟度的影响
DSH自建生态（alpha 期）~30 内置插件，生态早期
OC借力 VSCode 生态180 扩展，生态最丰富
HM自建 + MCP 标准65 optional-mcps，中等生态
ASR自建 + agentskills 开放标准早期，以确定性工具链替代生态

OC 借力 VSCode 生态是最聪明的冷启动策略——180 扩展不是自己写的，是 VSCode 生态的溢出。ASR 选择自建 + agentskills 开放标准，短期生态最弱，但以确定性工具链替代生态：不需要 180 个扩展，因为 plugingen 可以按需生成任意插件骨架。这是用"生成"替代"堆积"的不同路线。

根因总结：四项目的差异本质上是三个硬约束的组合选择——语言运行时决定热重载/隔离天花板，部署形态决定是否需要确定性生成，生态策略决定成熟度爬坡路径。ASR 的"设计领先、成熟早期"是"静态语言 + 多端部署 + 自建生态"组合的必然画像，而非设计水平的不足。

9RSI 自进化专题：ASR 的根本分水岭

本章基于 ASR 的 RSI 工程文档（specs/RSI/），深入剖析 ASR 在 D12 维度为何能突破"技能文本层"边界，以及这一突破的工程含义。

9.1 Iron Law RSI-0：确定性优先

Iron Law RSI-0：框架级确定性优先由确定性代码生成工具保障，以系统工程的确定性消解 LLM 在框架级变更中的不确定性。LLM 仍在需要的流程与位置生成代码（胶水逻辑、非标准实现等），只是不再让其概率性输出单独承担框架级结构正确性。

关键澄清：这不是"去 LLM"，而是让合适子系统特性由合适组件提供——确定性工具做确定的事，System-1 做结构化判断，System-2 做推理与创造，各司其职。 证据 B：specs/RSI/spec.md §1 组件定位 · specs/RSI/research.md §4

同业自进化只有"单腿"（技能文本层）。ASR 的 RSI 是三腿闭环——代码、技能、数据库三大基础设施的联动自进化：

9.3 五阶段循环：RSI 心跳

① 实测 → ② 根因 → ③ 优化方案 → ④ 防回退 → ⑤ 约束注入 ↻ 反馈（下一轮触发）

根本分水岭：同业的自进化是"LLM 写 memory/skill 文本 → 下一轮 LLM 读取"——文本进文本出，不改框架源码。ASR 的自进化是"LLM 规划 → 确定性工具生成源码 → 编译绿条 → git 入库"——产出的是已验证的框架代码变更。这一差异使 ASR 的自进化从"建议"升级为"已验证 PR"。

9.5 System-1 承接：双驱动框架

ASR 的确定性代码生成工具把"写框架代码"这一不确定任务，转化为"调用哪工具 + 传什么结构化参数 + 什么顺序"的结构化决策序列。而"结构化决策"正是 System-1 判断引擎（Laya 的 choice/score/noul 原语）的定义域：

  • 选操作 / 模块 / 模板 = Laya choice
  • 字段 / 参数取值 = Laya noul / score
  • 正确性核验 / 防回退 = Laya noul
  • 三态门控 = Laya 校准置信度（高→自动执行；中→提示人工；低→升级 System-2/人工）

这带来双驱动框架特性：ASR 有 AI 是 AI 驱动开发框架，无 AI 仍是完备框架（CRUD/权限/同步/调度照常）。同业 harness 无 AI 即瘫。这是 ASR 被称为"AI 驱动开发框架超越 harness"的底层原因。 证据 B：specs/RSI/design.md §2.4 System-1 承接 · specs/RSI/spec.md C11

11拓展 AgentSkills 标准的定位：拓展 vs 创新

ASR 对 agentskills 开放标准的态度是拓展而非颠覆——在既有 plugin 能力声明基础上新增 self-evolution 能力项，使 ASR 的 RSI 可被外部运行时探测。这一克制叙事是产品定位的选择。

11.1 拓展的边界

既有能力项（拓展不改）新增能力项（拓展加入）
  • plugin.inspect / plugin.activate / plugin.refresh
  • skill.execute / skill.list
  • tool.invoke / tool.schema
  • 既有 manifest schema + 生命周期
  • self-evolution.detect：探测运行时是否具备自进化能力
  • self-evolution.submit：提交自进化目标
  • self-evolution.status：查询自进化进度
  • self-evolution.artifact：获取已验证变更产物

11.2 为什么是拓展而非颠覆

  • 生态兼容：既有 agentskills 运行时无需改动即可忽略 self-evolution 能力项，向后兼容。
  • 渐进采纳：外部运行时可按需探测并使用 RSI，不强制。
  • 标准领导力：把"AI 驱动开发框架的差异化"从产品特性提升为行业标准，反向牵引生态——这是 P2-1 的战略价值。
  • 克制叙事：ASR 不宣称"取代"其他框架，而是"拓展"标准——在既有能力上叠加自进化，让市场自行选择。
定位总结：ASR 的产品定位是"AI 驱动开发框架"而非"AI Agent harness"——harness 无 AI 即瘫，ASR 无 AI 仍是完备框架（双驱动）。拓展 agentskills 标准是这一定位在标准层面的投射：不颠覆既有 Agent 生态，而是叠加"框架自进化"这一新维度。
