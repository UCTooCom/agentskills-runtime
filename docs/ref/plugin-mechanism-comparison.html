1. 评估方法与公平性声明

1.1 怎么做到的"公平"

这四个项目处在完全不同的成熟度阶段：openclaw 是已大规模分发的产品（版本号 2026.10.4）， hermes-agent 标称 1.0.0，deepseek-harness 自我声明为 0.2.1-alpha.3 的"开发者预览"， agentskills-runtime 为 v0.0.29。若直接按"现状谁更强"打分，等于用工程投入量碾压设计理念，这不公平。

因此本报告把每个维度拆成两个独立口径分别评估：

  • 设计完备度（Design）——机制在架构层面被设计到什么程度，是否覆盖了关键问题。看的是"想到了没有"。
  • 落地成熟度（Maturity）——该机制实际实现到什么程度、是否有生态规模支撑。看的是"做出来了没有"。
评分口径（1–5 分）
5 = 该维度业界一流 / 4 = 完整且可用 / 3 = 有方案但有明显缺口 / 2 = 只有雏形 / 1 = 基本缺失。
每个结论都尽量给出源码证据（文件路径 + 关键标识），而非文档转述。文档与代码矛盾时，以代码为准。

1.2 证据等级

等级含义本报告中的用法

1.3 边界声明

  • 本报告只看插件/扩展机制本身，不评价 Agent 能力、模型适配、UI 等其它方面。
  • 四个项目均为 MIT 系许可（ASR 为 MIT，其 package.json 元数据标 ISC，以仓库 LICENSE 为准）。
  • 缩写约定（全文与图表通用）：DSH = deepseek-harness，OC = openclaw，HM = hermes-agent，ASR = agentskills-runtime。ASR 即本项目，其缩写取自 AgentSkills-Runtime。
  • "插件"在各项目中叫法不同（plugin / extension / bundle / skill / MCP），本报告统一按"宿主能力的可装卸扩展单元"来理解，并在各章节标明其原生术语。

4. 分维度深度剖析

D1 · 插件的定义形态

deepseek-harness 把插件定义压到最简：一个导出 apply 的模块就是插件，并接受三种形状（函数 / 带 apply 的对象 / Service 子类）。 整个应用不是"代码启动框架"，而是 cordis.yml 组合出来的插件树——教程里明确写 "There is no framework bootstrap code in your file"。 这是"一切皆插件"最彻底的表达。

// docs/cordis-tutorial/01-first-plugin.md:11-19
export const name = 'hello'
export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}
// cordis.yml
- name: './hello.ts'

openclaw 走"包 + 清单"：扩展目录带 openclaw.plugin.json，声明 id、分类、激活条件、channel、configSchema。清单是 机器可读的能力契约，加载器照着清单决定给它什么。

hermes-agent 是 Python 生态的典型：既支持 setuptools entry-point 组 hermes_agent.plugins，也支持目录 + plugin.yaml， 插件入口是包里的 register(ctx)。

agentskills-runtime 用 plugin.yaml 描述，且每条带 mode 字段决定走哪条轨：

# src/plugin/plugin_config.cj:44-67（清单示例）
plugins:
  - name: memory-postgres
    className: magic.plugins.memory.MemoryPostgresPlugin
    mode: sync            # 缺省 sync；可选 sync/dylib/process
    order: 1
    config: { connectionString: "postgres://..." }
  - name: external-tool
    mode: process         # L3 进程隔离轨
    command: ./skills/external-tool/target/release/skill_external_tool.exe
    args: ["--log-level", "info"]
    autoRestart: true
点评（公平）：DSH 的"零样板"体验最好，代价是插件形态与宿主语言强绑定（必须 TS 模块）。 agentskills-runtime 的 mode 字段是四家里唯一把"隔离档位"写成清单一等公民的——插件作者显式选择跑在哪， 这在静态编译语言里是必要的（编译进宿主 vs 动态库 vs 子进程，代价差一个数量级）。DSH/hermes 的隔离是宿主全局开关， runtime 是逐插件声明，粒度更细。

D2 · 清单与版本契约

插件生态真正的难点不是"能不能装"，而是"装上去会不会因为版本不匹配把宿主搞崩"。四家的应对差异明显：

项目版本约束机制冲突时的行为
deepseek-harness安装前用 pnpm 解析 registry spec 的 peer deps 与 DSH 版本比对；不兼容直接拒绝plugin-manager/README.md:69拒绝 + 报错 incompatible-version；支持 compatibility.json 按 pkg@ver → runtime版本 精确豁免，但需 acceptRisk: true
openclawpackage.json 两个必填字段：openclaw.compat.pluginApi、openclaw.build.openclawVersionplugin-package-contract/src/index.ts:29-32缺字段即校验失败（listMissingExternalCodePluginFieldPaths）
hermes-agentrequires_hermes 版本范围 + requires_env + Python 依赖探测plugin_validate.py:115,164,576校验报告逐项列出（ValidationReport）
agentskills-runtime清单含 version，但未见宿主版本 range 约束的等价机制skills/hello/plugin.yaml—
agentskills-runtime 的明确短板：它的 Sync 轨是编译期合并进宿主的，版本冲突在编译阶段就暴露了，所以"运行时版本协商"的必要性确实低于其他三家（这不是偷懒，是静态语言的天然免疫）。 但 Dylib / Process 两轨一旦成熟，插件与宿主就是二进制 ABI 关系——那时候没有版本 range 校验会比动态语言更危险（动态语言不兼容只是报错，ABI 不兼容是段错误）。 建议：L2/L3 轨正式启用前，必须补 ABI/pluginApi 版本协商。

D3 · 发现与加载

  • deepseek-harness：Loader 插件读 cordis.yml，把每个 name 当模块说明符解析（相对路径或 npm 包名），并发挂载。关键设计：列表顺序不保证加载顺序，顺序由 inject 声明的服务依赖推导。
  • openclaw：activation-planner 解析清单的 activation 段（如 onStartup: false）决定激活时机，配合 discovery-state 做按需加载——懒激活是大生态的必要优化（180 个扩展不可能全启动）。
  • hermes-agent：入口组 + 目录扫描，另有 start_background_plugin_discovery() 把发现挪到后台线程，避免拖慢启动plugins.py:1774。
  • agentskills-runtime：PluginDiscoveryService.discover() 去中心化扫描 plugin.yaml；因为仓颉 LTO 会剪除未被静态引用的类，必须靠 build-sync 生成 generated_anchors.cj 显式实例化来"锚住"插件类spec.md §0.2 限制 #3。扫描到声明后，PluginLoader 经 ClassTypeInfo.get → findAnnotation<PluginAnnotation> → ConstructorInfo.apply 在运行期动态定位并实例化插件类，无需维护静态注册表——新插件放入目录即生效（零配置注册、热插拔）。
值得记的一点：DSH 用"依赖推导顺序"取代"声明顺序"，这是个真正的架构洞见——插件多了以后，人工维护顺序必然出错。 agentskills-runtime 用 order 数字字段排序，在 51 个 skill 规模下够用，但规模上去后会重蹈覆辙。

D4 · 隔离模型

这是四家差异最大、也最值得单独成章的维度，见 第 5 节专题。

D5 · 通信与 IPC

只有真正跨了进程的两家需要 IPC，它们的实现都很讲究：

  • hermes-agent 的 PluginHost 是一个相当完整的 RPC 层：Channel 传输、generation 代次（宿主重载后旧代次的调用被拒绝）、 对象代理（_ObjectSlot + _object_proxy，把插件侧对象的方法表发给宿主，宿主构造 ABC 子类，方法调用回到插件进程执行）。 还显式列出了"无法跨进程"的方法清单（HOST_UNSUPPORTED_CTX_METHODS）——比如需要原生 SDK client 的注册项，只能 in-process。
  • agentskills-runtime L3 用 JSON-RPC over stdio（ystyle::cordis_host.PluginManager(stdio)），并注明 UDS 不启用cordis_host_manager.cj:24,32。
hermes 的 HOST_UNSUPPORTED_CTX_METHODS 是本次调研里最有工程价值的一处细节。 它诚实地承认"进程隔离不是银弹"：有些能力天然需要活对象（原生 SDK client、event loop 绑定的 adapter、argparse parser）， 跨进程就拿不到。它的做法是把这些方法显式列成表 + 给出拒绝理由，而不是假装全部支持。 同一张表还被静态审计脚本复用（plugin_isolation_audit），保证"审计说安全"和"实际能加载"不会漂移—— 文档里原话："the audit says pool-safe and it loads in the host cannot drift apart"。 plugin_isolation.py:14-17

D6 · 生命周期与依赖注入

deepseek-harness 在这一项上是断层领先，Cordis 的 Fiber 模型提供了四家里最完整的语义：

  • Fiber 状态机：每个插件实例是一个 fiber，有 uid、state、config、store（依赖实现快照）。
  • 声明式依赖：export const inject = ['timer']，缺 provider 时 fiber 停在 PENDING 而非报错——因为 provider 可能稍后才挂载。这是"迟到的依赖"的正确处理。
  • 可逆卸载：ctx.effect() 注册的 disposer 在 fiber 卸载时逆序执行，且支持 async（卸载会 await）。这意味着插件真的可以被干净地摘掉。
  • HMR：fiber.restart() / update()，配合文件监听实现热重载。
  • 诊断：可遍历 ctx.registry 检查每个 fiber 的 state，专门对付"插件什么都不做也不报错"的静默失败。
// 诊断 PENDING 插件（06-composition-and-hmr.md:67-83）
for (const runtime of ctx.registry.values())
  for (const fiber of runtime.fibers)
    if (fiber.state === FiberState.PENDING)
      console.log(`${fiber.name} is PENDING — a required service is missing`)

agentskills-runtime 用"注解声明 + 反射发现 + 生命周期状态机"覆盖了六语义中的五个（Service / inject / effect / Events / 检视）， 事件总线实现 emit / waterfall 两种；HMR 明确延后，spec 里原话是"HMR/合流性无定理背书，对外只表述确定性插件生命周期"—— 这个自我标注很诚实，值得肯定。spec.md §0.2 限制 #6

hermes-agent 有 load/unload 回调、加载超时保护（插件超时后再调 ctx 会被忽略并记日志）plugins.py:1106。 openclaw 有独立的 activation-context / lifecycle / registry-lifecycle 模块。

D8 · 权限与安全模型

四家的思路可以分成两派："运行时审批派"（DSH）和"安装期声明比对派"（openclaw / hermes）。

deepseek-harness：运行时审批门

每次工具动作需要 danger-full-access 或逐次审批；低 sandbox 模式下 ask 请求批准、never 直接拒绝。 但它明确自述："installed Host code executes in-process outside the workspace sandbox"（宿主插件代码在进程内、工作区沙箱之外执行）， 且 SAFETY.md 开头就写 "It has not undergone a security audit and must not be treated as secure or production-ready"。 plugin-manager/README.md:31；SAFETY.md:3

5. 隔离模型专题：四种哲学

隔离模型是插件机制的分水岭——它决定了"敢不敢装第三方插件"。四家选择了四种不同的位置：

项目默认档可选档故障爆炸半径哲学
deepseek-harness进程内（in-process）动态定义跑 node:vm realm插件崩 = 宿主崩信任 + 审批 + 组合优雅性优先
openclaw进程内worker-runtime 任务池插件崩 = 宿主崩契约 + 清单声明 + 安装期同意
hermes-agentin_processhost（每 profile 一子进程）host 档下 = 仅插件宿主崩可切换；诚实标注哪些能力不能跨进程
agentskills-runtimeL3 process（plugingen 新插件默认；存量宿主模块 sync 且冻结）Dylib（动态库）/ Sync（内嵌）Process 轨 = 仅插件进程崩三轨并存；增量扩展一律 L3 插件化，宿主存量冻结只减不增

关键原文（避免误读）

# hermes_cli/plugin_isolation.py:3-12（模块 docstring）
in_process (default) imports every plugin into the Hermes process, as always.
host keeps third-party plugin code OUT of it: general plugins load in one
plugin-host process per profile and talk to Hermes only through ctx ...
That second half is the property a pooled deployment needs: one Hermes process
serving many profiles must never share an interpreter with a profile's plugin code.
The same boundary gives a single-user install crash isolation (a plugin that
segfaults or hangs takes down its host, not the gateway).
hermes 这段话说得最透彻：进程隔离不只是为了防恶意插件，更是为了部署形态—— "一个 Hermes 进程服务多个 profile"时，绝不能和某个 profile 的插件代码共享解释器。 顺带还白拿了崩溃隔离（插件段错误只崩宿主进程，不崩 gateway）。 这个"一份设计同时解决多租户和稳定性"的思路，值得 agentskills-runtime 在 L3 轨推广时借鉴。
公平地说 DSH：它选进程内不是不懂隔离，而是权衡后的选择—— Cordis 的全部优雅性（Fiber、inject、effect 逆序清理、HMR）都建立在"插件与宿主共享同一个 Context 对象图"之上， 一旦跨进程，这些语义全要重写成 RPC。它的补偿手段是审批门 + 明确告知风险（SAFETY.md 直言未安全审计、不要作为唯一安全控制）。 这叫"把风险讲清楚后让你自己承担"，也是一种负责任的做法，只是不适合跑不可信代码。

7. 成熟度校正评分

deepseek-harness openclaw hermes-agent agentskills-runtime（ASR）

7.1 设计完备度（看"想到了没有"，不看工程量）

7.2 落地成熟度（看"做出来没有 + 生态规模"）

怎么读这两组分数： deepseek-harness 在"设计完备度"上领先，但它是 alpha、自述未审计；openclaw 在"落地成熟度"上领先，因为它的设计是"够用即可 + 大规模铺量"。 ASR 的设计完备度不低（三轨、tableWhitelist、plugin+SKILL 三维一体、状态机、确定性代码生成工具链（代码腿）都是真设计）， 但成熟度受两个硬约束拖累：仓颉工具链限制（cjpm workspace/package 互斥、LTO 剪除、动态库符号冲突）和项目阶段。 把这两组分开看，才能避免"用成熟度否定设计"或"用设计掩盖没做完"。
新增两维（D11 / D12）的读法： D11 里 ASR 拿到设计 4 / 成熟 2 的落差分——plugingen 能一键生成可独立编译的 L3 工程（设计上是四家里唯一敢把"最安全那轨"设为默认的）， 但模板不带测试、没有插件侧校验器、权威文档躺在 .codeartsdoer/specs/ 隐藏目录里，第三方作者实际用不起来。 D12 的分水岭在第二层——OC 让模型自写技能且后台自动评审、HM 有完整技能层闭环但契约禁止动代码、ASR 独辟"代码腿"（确定性工具链实际演进框架代码）、DSH 则完全没有这条链路。 ASR 在"自进化能不能碰代码"上是四家里唯一突破"技能文本层"的：它把 RSI 做成 code+skill+database 三腿闭环，由确定性代码生成工具承载代码演进（设计 5 / 成熟 4）；其唯一待补的是 DB 腿（UMI-ORM 未完整）与"每 N 轮后台自评"的常驻触发。

8. 根因解读：为什么它们如此不同

看完十二维度会有个疑问：同样是"Agent 框架的插件机制"，为什么能差这么多？答案不在设计品味，在三个硬约束：

约束一：语言与运行时——决定论级别的影响

语言特性带来的能力失去的能力
TypeScript / Node（DSH、openclaw）运行时 import、模块热替换、Proxy 拦截 ctx、动态对象图无法做真正的进程隔离（除非显式起子进程/Worker）
Python（hermes）entry-point 组、运行时 import、丰富的动态能力同左；GIL 使"进程内多插件"并发受限，反而推动它做进程隔离
仓颉（agentskills-runtime）原生二进制、类型安全、跨平台单一产物HMR 基本不可能；LTO 剪除未引用类 → 需反射锚点；动态库需 --dy-std；workspace/package 互斥

agentskills-runtime 的 spec 里把这三条写得非常直白（限制 #1/#3/#4/#5），并逐条对比了"与 DSH 的差距"。 这种把自家短板写成正式文档的态度，本身就是工程成熟度的体现——比粉饰报告有价值得多。spec.md §0.2

约束二：部署形态

  • DSH 是开发者本机工具（CLI + Desktop + Web），所以"审批 + 告知风险"够用，不需要强隔离。
  • hermes 明确要支持池化部署（一个进程服务多 profile），所以必须有进程隔离——这直接决定了它的双档设计。
  • openclaw 要接 180 个外部集成（大量是 model provider），稳定性靠"契约 + 清单"而非隔离。
  • agentskills-runtime 定位含插件市场（v1.0 基础设施 / v1.1 上线），要跑第三方二进制 → 必须有 L3 进程轨。

约束三：生态冷启动策略

四家对"谁来审核插件"给出了四种答案：DSH = 用户自己批准；openclaw = 安装时能力比对 + 用户确认； hermes = 机器探针验证声明一致性 + MCP 走 PR 人工评审；agentskills-runtime = 目前主要靠自带 skills 目录。 没有对错，只有阶段适配——市场为空时 PR 评审最稳，规模上来后必须自动化。

9. 对 ASR（agentskills-runtime）的启示

基于上面的实证对比，按性价比排序给出建议（先做收益最大、成本最低的）：

优先级建议借鉴自理由 / 预期收益
P0 给 Dylib / Process 两轨补版本协商（pluginApi range + 宿主版本 range，不符拒绝加载） openclaw openclaw.compat.pluginApi；DSH peer 校验 ABI 不兼容在原生二进制下是段错误而非异常，风险远高于动态语言。这是 L2/L3 启用前的硬前置。
P0 L3 进程启动后做"能力宣告握手"：插件上报将注册的 Service/Route，宿主与 plugin.yaml 声明比对，不符拒绝挂载 hermes 能力探针 _check_capabilities 二进制插件用户无法审查，声明一致性必须由机器验证。成本是一次握手，收益是防住"偷偷多注册"。
P1 把 tableWhitelist 扩成通用能力清单（网络出口、文件、子进程、环境变量…），缺省全拒 openclaw capabilities；hermes 多维校验 目前只管 DB 表，是最窄的一家。L3 轨一旦跑第三方代码，覆盖面必须补齐。
P1 公开声明"哪些能力不能跨进程"（对应 hermes 的 HOST_UNSUPPORTED_CTX_METHODS），并让静态审计复用同一张表 hermes plugin_isolation.py 避免"审计说安全"和"实际能加载"漂移。runtime 已有 cordis-cj 集成，这张表是 L3 推广时的必需品。
P2 用依赖推导替代 order 数字排序（插件声明所需 Service，由注册表拓扑排序） DSH inject + PENDING 51 个 skill 时 order 够用，规模上去了必然维护失控。DSH 已证明这条路可行。
P2 给 L3 轨加崩溃自愈的可观测性（重启次数、退避策略、崩溃原因上报） DSH install 状态机；hermes generation 代次 autoRestart: true 已有，但缺"重启风暴"防护——一个启动即崩的插件会无限重启。
P1 plugingen 模板自带一个"跑得起的最小测试"，并补独立 plugin validate openclaw plugins init 生成 index.test.ts + vitest.config.ts；hermes plugins doctor 走真运行时验证 D11 是四家里 ASR 设计分与成熟分落差最大的一项（4 / 2）。生成器已经很强，缺的恰恰是"让第三方作者敢改"的那一步——一个模板自带的测试 + 一条校验命令，成本极低、收益极高。
P1 把 RSI 三腿闭环从"工具就绪"推进到"常驻自进化循环"：补"每 N 轮后台自评"触发 + 将确定性代码腿接入 LRT 五环节 openclaw skills.workshop.autonomous.mode: auto（累计 N 轮后台自评）；hermes background_review 每轮后 fork 自评 ASR 的代码腿工具链（loaddbinfo / crudgen / crudweb / plugingen / pluginuninstall）已就绪且生产可用，LRT 五环节（实测→根因→优化→防回退→约束注入）也已在 src/app/services/lrt 落地； 当前缺口是把这些确定性能力串成一个"每 N 轮无条件后台自评"的常驻循环（目前多在长程任务失败时或按需触发）。OC/HM 的做法是"每 N 轮后台自评一次"——把自进化从"出错才修"变成"常态沉淀"，是 D12 里最该补的一档分。
保持 plugin + SKILL.md 三维一体、三轨 mode 声明、"代码腿"确定性自进化（loaddbinfo / crudgen / crudweb / plugingen / pluginuninstall）、spec 里诚实标注限制条款 — 这四项是 ASR 的真实差异化优势，四家里独一份 —— 尤其"以确定性代码生成工具承载框架自进化"这条路线， 是 DSH / OC / HM 三家都没有的（它们把自进化锁死在技能文本层）。这是 RSI 议题上最值得对外讲的一点，也是其"AI 驱动开发框架"定位的硬核支撑。
最需要正视的一条：agentskills-runtime 的 Sync 轨"改一行要重编宿主（约 51 分钟）"， 这在开发体验上是四家里最差的，且短期无法通过设计优化根治（静态语言决定的）。 但这一点 ASR 已用工程与规范落地化解，而非停在建议层：开发者插件生成工具 plugingen 的缺省轨就是 L3 process（plugingen.cj:48 写死 var mode = "process"）， sdd / uctoo-dev-manual 技能与《模块开发规范》SOP 更明文要求"能做成插件就做插件"、宿主 src/app/ 存量模块"存量冻结、只减不增" （sdd/SKILL.md:285,397,414；uctoo-dev-manual/SKILL.md:70,353；feasibility.md 附7.9；design.md §1.0；tasks.md(AgenticSoftwareFactoryHackathon):17）。 亦即新扩展一律走 L3 插件、Sync 轨仅留给无法解耦宿主的极少数存量能力——三轨设计的价值不仅没有被默认档抵消，反而因"默认即最安全那轨 + 宿主冻结"成为 ASR 的真实差异化（呼应 §D11：四家里唯一敢把最安全轨设为默认）。 真正剩下的硬前置是 L2/L3 正式对外跑第三方二进制前必须补齐的 ABI / pluginApi 版本协商、L3 能力宣告握手、崩溃自愈可观测性（见 §风险与对策），而不是"是否该把默认档切到 L3"。

11. 拓展 AgentSkills 标准的定位：拓展 vs 创新

本报告第 3、7、9 章已记录 ASR 在 D7「一切皆技能」维度上的事实——拓展 AgentSkills 开放标准支持仓颉静态二进制发布、plugin + SKILL.md 三维一体、三轨 mode 声明。本节把"这到底算不算对 AgentSkills 标准的拓展与创新"做一个明确的定位判断，供对外叙事（赛事 / 文档 / 论文）引用。

11.1 结论速览

判断项结论成立条件
是否"拓展"是，站得住保留 SKILL.md + scripts/ 开放契约不变，在执行底座上新增一条"静态编译原生二进制"轨道，这是原生标准没有预见的。
是否"创新"是，但需正确表述创新点是组合架构，不是"多支持了一门语言"；单说"支持了仓颉"只是增量，不构成创新。

11.2 为什么"拓展"成立

原 AgentSkills 标准（deepseek-harness 那条线）的技能脚本是运行时解释执行的——JS 走 node:vm eval、Python/TS 走解释器，隐性假设"技能源码是可读、可即时运行的文本"。ASR 做的事是：

  • 保留 SKILL.md + scripts/ 契约不变；
  • 在执行底座上新增仓颉轨：先 cjc --output-type=dylib 编译成 .so/.dll/.dylib，再用 PackageInfo.load() 反射加载、运行时实例化（见 cangjie-plugin-system-feasibility.md 第 146、153、805 行）。
这条轨道是原生标准没有预见到的：原标准从没要求宿主具备"编译 + OS 动态链接 + 反射实例化"的能力。所以"拓展"用得对——扩的是执行 substrate，不是另起炉灶。

11.3 "创新"成立靠的是组合拳，不是单点

真正算创新、值得写进赛事叙事的有四点（已在本文 D7 维度记录证据）：

  • 静态二进制作为一等公民技能：把静态编译语言做成 AgentSkills 兼容框架里的"技能/插件"，而非"调个外部进程"。
  • 三轨隔离 mode 写进清单一等公民（sync | dylib | process）：四家里唯一把隔离档位写成清单字段的，且是静态语言的刚需——编译进宿主 vs 动态库 vs 子进程，代价差一个数量级；DSH/hermes 是宿主全局开关，ASR 是逐插件声明。
  • "三维一体"：plugin + SKILL.md + scripts 统一。dsh 的"一切皆插件"是代码组织层面的统一；ASR 的"一切皆技能"是 AI 可理解行为 + 可执行代码 + 可管理插件的统一，维度高一层。
  • 闭源分发：dylib 二进制可不开源，JS 必须可见（feasibility.md 第 1540 行）。对编译型语言是实打实的能力差。
必须避开的坑：单说"我们支持了仓颉这门静态语言"不是创新，只是"多支持一种语言"——Java SPI/ServiceLoader、OSGi、.NET MEF、原生 dylib 插件都是几十年前的东西。"动态库加载插件"是教科书操作，没人会为这个给一等奖。

11.4 对外叙事建议（克制、可落地）

不要写"颠覆性创新""比 dsh 更原生智能"这类营销断言（本报告刻意未写入，保持客观）。建议定调为：

建议表述
对 AgentSkills 开放标准的务实拓展：在保留 SKILL.md 契约的前提下，将静态编译型语言（仓颉）原生二进制纳入技能执行底座，并以"三轨隔离声明 + 框架插件机制与智能体技能机制三维一体融合"的架构，补上了动态脚本标准在确定性、隔离粒度、闭源分发上的空白。

真正能撑起"创新"叙事的，是 RSI 主线——"以系统工程的确定性消解 LLM 的不确定性"：静态编译 + System-1 决策引擎接管结构化决策，才是这套拓展背后真正有别于"加一门语言"的原创贡献。赛事材料里应把"支持仓颉"作为论据而非论点。
