# FFI 静态链接部署结论（2026-04-29）

## 问题

是否可以用 C 实现算法，然后在仓颉项目中使用，但不额外携带 `xx.dll/xx.so` 这类外部动态库？

## 结论

可以做到“**不携带你自己的动态库**”，方式是：

1. 将 C 算法编译为静态库（如 `.a` / `.lib`）。
2. 在仓颉编译阶段通过 `-L/-l`（`--library-path/--library`）链接到最终产物。

这样 C 算法代码可以被链接进最终二进制，不需要单独分发自定义 `dll/so`。

## 关键边界

1. 这是“业务 C 库无动态依赖”的结论，不等于“程序绝对零动态依赖”。
2. 是否可做到几乎全静态，和平台强相关：
   - Linux：更容易做到，仓颉文档支持 `--static`（全静态链接仓颉库）。
   - Windows/macOS：通常仍需关注运行时与系统库策略，不能简单等同 Linux。
3. 若使用动态库链接路径，则运行环境仍需配置动态库搜索路径（`LD_LIBRARY_PATH`/`PATH` 等）。

## 工程建议

1. 优先采用“C 静态库 + 仓颉 FFI 声明”方案，避免分发自定义 `dll/so`。
2. 按目标平台分别验证最终产物依赖，不假设跨平台行为一致。
3. 性能上，FFI 仅适合粗粒度调用；细粒度高频跨边界调用在本项目中已多次实测不占优。
