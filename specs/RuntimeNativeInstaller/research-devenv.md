## 原始需求（用户原话，未改写）

> 好的，我们已经研究了和 NestJs 对标的进行 runtime 发行版安装的功能需求，另外，其实还有一种类型的安装，就是给二次开发的开发者安装 runtime 开源项目，进行二次定制开发。这个安装需求应如何补充实现？业界一些成熟方案看起来是在发行版安装后，询问是否安装开发包，例如，postgresql 等数据库就是在安装完数据库发行版后有是否需要安装开发套件的选项。请增加研究安装和初始化 runtime 本地开发环境的方案，这个部分的需求原 NestJs 不覆盖，可以参考我们 runtime 本地开发环境进行研究。

拆解为四条硬约束（本文档逐条回应）：

1. 这是**第二种安装类型**，目标人群是**二次开发开发者**，不是最终用户；
2. 交互范式对标 **PostgreSQL installer 的「装完发行版再问要不要开发套件」**；
3. 原 nestJs 引导程序**完全不覆盖**，是新增需求；
4. 研究依据 = **逆向归纳本项目 runtime 本地开发环境本身**（一台能跑二次开发的机器到底需要什么）。

### 1.3 三个最容易踩空的技术点（展开）

**（1）仓颉 SDK 本体从哪来 —— 已查清**

- 仓库内**没有** vendored SDK。`libs/` 只含 stdx 与第三方库（实测 178.9 MB），编译器本体在机器上的 `d:\Program Files (x86)\Cangjie`（1.2 GB）。
- 官方发布页（`https://cangjie-lang.cn/download/1.1.3`，发布 2026/05/29）同时提供 **exe 安装版（127.38 MB）** 与 **zip 免安装版（373.96 MB）**。zip 版解压即用，是**离线预置的唯一可行形态**：解压后目录内自带 `envsetup.bat`/`envsetup.ps1`/`envsetup.sh` 与 `uninstall.exe`。
- SDK 自带 `Cangjie.url`，内容为 `URL=https://cangjie-lang.cn`（作为来源溯源标记）。
- ⇒ 结论：开发套件的「SDK 组件」应优先采用 **zip 免安装版 + 调用官方 `envsetup.bat` 或直接复刻其 12 行的环境变量写入逻辑**，而不是 exe 安装版（后者是交互式 GUI，无人值守困难）。

**（2）stdx DLL 如何落到正确位置 —— 双轨并存，必须区分**

本机存在两套 stdx 引用约定（工程记忆 `.workbuddy/memory/2026-08-28.md:56-81`）：

- 轨道 A（宿主侧库，如 jwt4cj / logcj / pgsql）：写 `${CANGJIE_STDX_PATH}/windows_x86_64_cjnative/dynamic/stdx`，即**环境变量指顶层、再拼子路径**；
- 轨道 B（cordis-cj 系与插件子工程）：写**显式相对路径**，如 `skills/llm_channel_tokendance/cjpm.toml:27` 的 `"../../libs/cangjie-stdx-windows-x64-1.1.3.1/windows_x86_64_cjnative/dynamic/stdx"`。

已实测的踩坑：`CANGJIE_STDX_PATH` 若错指到 cjo 子目录，会拼成 `.../dynamic/stdx/windows_x86_64_cjnative/dynamic/stdx`（路径翻倍）而编译失败。⇒ 安装器写入该环境变量时**必须写顶层目录**，并把这条双轨约定写进自检判据。

**（3）OpenSSL DLL 命名坑 —— 开发态与发布态都要处理**

`libcangjie-dynamicLoader-opensslFFI.dll` 把 `libcrypto-3-x64.dll` 写死在 PE 导入表（1.1.3.1 版本字节偏移 126720，见 `runtime-openssl-dll-guide.md:35,40-42`）。stdx 包内不携带任何 `libcrypto*.dll`；SDK 自带的那份叫 `libcrypto-3.dll`（**少 `-x64`**）→ 加载器不认 → 系统若装 OpenSSL 4.x 则 100% 失败，业务表象是「登录 401」。

修复方式（方案 A，见 `runtime-openssl-dll-guide.md:56-68`）：把 runtime 自己的 `libcrypto-3.dll` 复制一份改名 `libcrypto-3-x64.dll` 放进 exe 目录。本机 `target/release/bin/` 实测**已同时存在** `libcrypto-3-x64.dll`（5,191,960 B）与 `libcrypto-3.dll`，说明该修复在本机已生效。

⇒ 开发套件**必须**包含这一步；发布态已在 `src/scripts/package_release/main.cj` 有对应步骤，开发态（`cjpm run`）仍需安装器补一次。

- **唯一路径 `git clone`**（2026-10-07 用户拍板，**取消离线复制兜底**）：得到带完整历史的工作副本，可切分支、可提交 PR、可 `revert`——这才是"二次开发"该有的形态。
- **不再设离线兜底**（拍板原文：「其他开发者没有我本地的开发目录，也无从复制源码，就只给其他开发者从开源仓库 git clone 的一条路就可以了」）。理由补充：离线复制的"来源"只能是本项目作者本机的目录，对任何外部开发者都不可得；为一条实际不可达的路径保留代码分支与来源标记机制（`.SOURCE_PROVENANCE` / `gitHistory:false`）属于没有受益方的复杂度。git 不可用或网络不可达时，**明确失败并给出可执行的处置指引**（安装 git / 检查网络 / 换镜像地址），不以任何形态的"降级副本"收尾。
- **目标目录选择步骤**（用户明确提出）：安装器必须让开发者指定 clone 到本机哪个目录，并对"不存在 / 存在且为空 / 存在且非空（细分：已是本仓库且 remote 匹配 → 复用并 `git fetch`；非空且非本仓库 → 拒绝并要求更换或显式确认）"三分处理；还需校验路径合法性、可写性与"不与发行版安装目录重叠"。
- **两个目录的关系**：开发者源码目录与发行版安装目录是**两个不同目录**，S8 初始化的工作目录必须指向前者，避免初始化动作打到后者。
- **与 DK-5 的联动**：clone 下来的源码树自带脚手架与 `skills/uctoo-dev-manual/`，DK-5 仍为零额外安装；但 `db_info` 必须再跑一次 `loaddbinfo` 刷新，**不因走了 clone 路径而可以跳过**。

详细设计见 `spec.md` §5.14（REQ-RNI-071~~077 / AC-166~~187）与 `design.md` §4.10.1.1。

## 三、交互范式与状态机集成

### 3.1 推荐形态：**S6 之后的 S7（开发套件）+ S8（初始化），并且可重入**

在 `research.md` 4.2 的 S0~S6 状态机之后追加两个步骤，形成 S0 → … → S6 → **S7 → S8**：

```
S6 起进程 + 轮询 /api/v1/health == 200   ← 发行版安装完成（最终用户到此为止）
        │
        ▼
S7  开发套件询问（可跳过，默认按 S0 探测结果预勾选）
        ├─ 不装 → 写入 .install-state.json: devkit=skipped，安装器自退出（最终用户模式）
        └─ 装   → 逐组件安装 DK-1..DK-8，每组件装完立刻跑自检，失败即标红并允许重试/回滚
        │
        ▼
S8  初始化（I1..I9，见 §五）→ devkit verify --json 全绿才算「可开发」
```

三个入口并存（避免「只有一次性弹窗」的 PostgreSQL 式缺陷）：

| 入口  | 形态                                                                                                | 适用场景                              |
| --- | ------------------------------------------------------------------------------------------------- | --------------------------------- |
| 向导内 | S6 完成后的**组件勾选页**（不是"装完就消失的一次性提示"）                                                                 | 图形交互、首次安装                         |
| CLI | `ucInstaller.exe --with-devkit[=DK-1,DK-3,...]` 与 `ucInstaller.exe --devkit-only`                 | CI / 无人值守 / 二次补装                  |
| API | 新增 `/api/setup/devkit/components`（清单+探测推荐）、`/api/setup/devkit/install`、`/api/setup/devkit/verify` | 与既有 16 端点同构；供后续 Stage B L3 薄适配器复用 |

### 3.2 为什么优于 PostgreSQL 的「装完再问」做法（落到可验证机制）

PostgreSQL/EDB installer 的实际做法是：安装过程中有 `Select Components`（PostgreSQL Server / pgAdmin 4 / Stack Builder / Command Line Tools），**安装结束前**弹一个 checkbox 询问是否启动 Stack Builder（`enterprisedb.com` 官方文档原文："Before the setup wizard completes the PostgreSQL installation, it offers to launch Stack Builder at exit"）。它有三个可被验证的具体缺陷，本方案逐条对应：

| # | PostgreSQL 做法的缺陷（有据可查）                                                                          | 本方案的对应机制（可验证）                                                                                                                                     |
| - | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **Stack Builder 是进程外的第二个安装器**：勾选后启动另一个程序，其成败**不进入**主安装器的状态与回滚域                                  | DK 组件安装是**同进程**的 S7 步骤，每步写 `.install-state.json`，可断点续装；失败可 `--rollback`（复用 `research.md` T3 的 staging + `previous/` 机制）                           |
| 2 | **组件选择在「安装前」，用户此时无法判断自己要不要 dev headers**                                                        | 组件选择在 **S6 之后**：此时 S0 已探明本机事实（是否已有 cjc 1.1.3、`CANGJIE_STDX_PATH` 是否指向顶层、OpenSSL 是否为 4.x、磁盘剩余空间），据此**预勾选 + 给理由**（例："检测到已装 cjc 1.1.3 → DK-1 默认不勾选"） |
| 3 | **装完不算能用**：官方文档原文 "By default, the installer doesn't modify the system path"，`psql` 要用户手工加 PATH | 每个组件**携带自检判据**（§二表第 6 列），S8 末尾跑 `devkit verify --json`，**自检不通过即宣告"未安装完成"**，并输出可执行修复命令（复用 `research.md` T8 的机器可读契约 + 非零退出码）                        |
| 4 | Stack Builder 需联网下载驱动/插件                                                                        | 离线优先：优先用仓库内已 vendored 的 stdx、源码树、sql 基线；缺失才回落官方镜像（复用 `research.md` T5）                                                                            |
| 5 | 只有"装"，没有"初始化"（建库、导基线、刷新元数据缓存）                                                                   | 显式 S8 初始化步骤 + 判据（§五）                                                                                                                              |
| 6 | 组件勾选只有一次机会，事后要另找工具                                                                              | `devkit/components` 端点与 `--devkit-only` 支持**事后重入补装**                                                                                              |

### 3.3 最终用户模式 vs 开发者模式

建议：安装器**默认最终用户模式**（S0~S6 走完即自退出），开发者模式由以下任一条件触发：CLI 传 `--with-devkit`、向导页勾选、或首次启动检测到"源码树已存在"。两者的可观测差异写进 `.install-state.json` 的 `mode` 字段，供后续排查与 Stage B 复用。
